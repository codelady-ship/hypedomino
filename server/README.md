# server

Go game server: WebSocket gateway (binary protobuf), rooms, matchmaking, accounts, economy. PostgreSQL and Redis.

Game rules live in one pure package, `server/internal/rules`, implementing [docs/rules.md](../docs/rules.md) (Epic 3).

## Run

```
cd server && go run ./cmd/server
```

The binary reads its configuration from the environment only (CLAUDE.md: secrets and tunables never live in code) and logs JSON lines to stdout. `SIGTERM` or `SIGINT` starts a drain: `/readyz` turns 503 so the load balancer stops routing, no new room opens and no new WebSocket is accepted, live matches play to their end (bounded by `HD_DRAIN_TIMEOUT`), then connections are closed with 1001 `server shutdown` and the listener stops (`docs/launch-runbook.md` 5.1: never kill a node with live rooms).

`/healthz` answers 200 while the process runs. `/readyz` answers 200 while the server accepts work and 503 from the first drain step on. A bad value in the environment stops the start with every bad variable named, exit code 2.

## Container and deploy

`server/Dockerfile` builds a static binary into a distroless image that runs as user `65532` (ADR 0010). Kubernetes manifests are in `deploy/k8s`: `base` is shared, an overlay per environment sets the image tag, replicas and the `server-env` secret. Locally, with Docker and kind:

```
docker build -t hypedomino-server:ci server
bash tools/deploy/container-smoke.sh hypedomino-server:ci
kind create cluster --name hd
bash tools/deploy/kind-rollout.sh hd hypedomino-server:ci
```

`terminationGracePeriodSeconds` in `deploy/k8s/base/server.yaml` must stay above the 10 s `preStop` plus `HD_DRAIN_TIMEOUT` plus `HD_SHUTDOWN_TIMEOUT`; change them together.

The gateway takes a `gateway.Handler`: it receives the accepted `ClientHello` and returns a `gateway.Session` that gets decoded intents with their sequence numbers. A `LoadingIntent` carries no sequence and is never acknowledged; it reaches the session as `Loading(progress, ready)`. `gateway.JoinRoom` and `gateway.ResumeRoom` bind a session to a room seat. A closed connection disconnects the seat without leaving it (`docs/penalties.md`: a short disconnect is not a leave); turns missed meanwhile are timeouts.

Sign-in (#57, ADR 0004: account flows use HTTPS on the same backend): the client calls `POST /auth/nonce` and gets `{"nonce"}`, passes the nonce to the provider (Google: as is; Apple: its SHA-256 hex, set per provider in `idtoken.Config`) and posts `{"provider":"google"|"apple","id_token","nonce"}` to `POST /auth/signin`. The server verifies the token once (`idtoken.Verifier`; the nonce is consumed, so a replayed token is rejected), finds or creates the account by provider and subject (`account.Store.SignIn`), and answers `{"session_token","account_id","created"}`; the session token is the resume token of `session.Manager` the WebSocket hello presents, until #58 replaces it with access and refresh tokens. Refusals are JSON `{"error"}` with 400 `malformed` or `unknown_provider`, 401 `token_rejected`, `token_expired` or `nonce_rejected`, 403 `banned`, 410 `deleted`, 503 `provider_unavailable` when the provider keys cannot be fetched. Bodies above 16 KiB are refused. The routes exist only with `HD_DATABASE_URL` and `HD_TOKEN_KEYS`; nonces live in Redis (`auth.RedisNonces`, shared by every node) when `HD_REDIS_URL` is set and in process memory otherwise. Rate limiting of sign-in is #184.

Session tokens (#58): the access token is an HS256 JWT (`iss`, `sub` account, `sid` session family, `dev` device, `iat`, `exp`) signed by the first key of `HD_TOKEN_KEYS` and verified by any listed key, so a new key is added in front and the old one removed once every token it signed expired (`docs/environments.md` 5). It lives `HD_ACCESS_TTL` and is what `ClientHello.session_token` carries; `session.Manager` authenticates it and keys the resume session by `sid`, so a refreshed access token resumes the same seat. The refresh token is opaque (family id and a random secret, only its SHA-256 stored) and rotates on every `POST /auth/refresh` `{"refresh_token","device_id"}` → `{"access_token","refresh_token","expires_in","account_id"}`, sliding its lifetime to `HD_REFRESH_TTL`. A refresh token presented after it was rotated, or from another device, revokes the whole family (`refresh_reused`), so a stolen token ends the session for the thief and the owner alike; a retry within `HD_REFRESH_REUSE_GRACE` after a lost response rotates again instead. `POST /auth/logout` `{"refresh_token"}` ends that device, `POST /auth/logout-all` with `Authorization: Bearer <access token>` revokes every family of the account and closes its live WebSocket connections; both answer 204. Other refusals: 401 `refresh_rejected` (unknown, revoked), `refresh_expired`, `access_rejected`, `access_expired`.

Profile (#59): every profile route needs `Authorization: Bearer <access token>` (401 `access_rejected` or `access_expired`). `GET /profile/me` answers the caller's own view `{"account_id","nickname","setup_required","suggested_nickname","rename_available_at","level","xp","loadout":{"avatar","frame","character","table","emojis"},"stats":{"games","wins","losses","win_rate_percent","streak","best_streak","modes":{"1v1":{...},"2v2":{...}}}}`; before the first nickname `setup_required` is true and `suggested_nickname` carries a free server-generated `Player<digits>` name. `PUT /profile/nickname` `{"nickname"}` creates the profile on first use and renames it afterwards: the text is normalised (NFKC, format characters stripped, whitespace collapsed) and stored as typed, while uniqueness uses the folded key (`profile.Key`: case folding with the Turkish i rule plus the Latin/Cyrillic and az/tr confusable table) checked inside one transaction against live profiles and the names replaced less than `HD_NICKNAME_RELEASE` ago, backed by the unique index on `profiles.nickname_key`. The first rename after setup is free; later ones wait `HD_NICKNAME_RENAME_COOLDOWN` and every replaced name goes to `nickname_history`. Refusals: 400 `malformed`, `nickname.invalid_length`, `nickname.invalid_characters`, `nickname.invalid_separators`, `nickname.mixed_scripts`, `nickname.digits_only`; 409 `nickname.taken`; 429 `nickname.cooldown` with `retry_at`. `GET /profile/{account}` is the public view of `docs/privacy.md` section 5: `account_id`, `nickname`, `level`, `loadout` and `stats.games`, `win_rate_percent`, `best_streak` only (404 `profile.unknown`). `profile.Store.RecordMatch` updates the statistics per match and mode; the room result hook that calls it, the word filter and reserved names (#60), equip with ownership checks (#61), level and XP progression (#62), the rename price (#101) and the attempt rate limit (#184) are separate issues.

Inventory (#61): the catalog is `cosmetics.Catalog`, loaded from `HD_COSMETICS_MANIFEST` or built in. Every live item with a `default` source is owned by every account without a row; everything else is an `inventory_items` row with its granting source, which `inventory.Store.Grant` writes only when the item's `sources` list that source (a revoked row is reactivated, an owned item is reported as not granted so the bundle engine of #102 can pay duplicate compensation). `Revoke` marks the row and unequips the item in the same transaction; a default item cannot be revoked. `GET /inventory` answers `{"items":[{"id","type","source_type","source_ref","granted_at"}],"loadout"}` and `PUT /inventory/equip` `{"slot","items"}` sets one slot: `avatar`, `frame`, `character` and `table` take exactly one item, `emoji` up to `HD_EMOJI_SLOTS`, `action` up to `HD_ACTION_SLOTS`; every item must exist, be of the slot type, be `live` or `retired` and be owned (400 `malformed`, `slot.unknown`, `slot.too_many`; 404 `item.unknown`; 403 `item.not_owned`; 409 `item.wrong_type`, `item.disabled`, `profile.setup_required`). `inventory.Store.Freeze` is the loadout other players see and what the opener records per seat in `match_participants.loadout` (`matchstore.Participant.Loadout`, NT-9): it re-checks every equipped item and replaces a missing, disabled or no longer owned one with the first live default of its type. Both views show that resolved loadout; the stored one changes only through equip and revoke. Admin grant and revoke call the store methods; their HTTP surface comes with the admin API.

Wallet (#101): coins change only through `wallet.Store.Apply(entry)`, one transaction that creates the wallet row on first use, locks it (spends of one account are serialised), returns the earlier result unchanged when the account already has an entry with that idempotency key (V-8: the repeat is answered with `Repeated` and writes nothing), refuses a result below zero (`ErrInsufficient`, so a race of spends lets exactly the affordable ones through), appends the `ledger_entries` row with the balance after and the config version, and stores the new balance. Every reason of `docs/economy.md` section 5 has a fixed sign (`admin_adjust` either), and a `purchase` key is unique across accounts (`ErrPurchaseReuse`), so a store transaction is granted once. `Audit` lists every wallet whose stored balance is not the sum of its entries and `Reconcile` sets it to the sum under the lock; `cmd/wallet-audit` runs both. `GET /wallet` with the access token answers `{"balance","entries":[{"id","amount","reason","source_type","source_ref","balance_after","at"}]}`, newest first, at most 50. The callers (match rewards, bundles, shop, rename, refunds) are their own issues; a `refund_revoke` entry may take the balance below zero since migration 00008 (#106); every other debit is refused while it is negative.

Table background (#98): at match start the opener takes every seat's frozen table (`inventory.Store.Freeze`), draws 32 bytes with `cosmetics.NewDraw` and calls `Catalog.Table(tables, rarities, draw)`: a missing, unknown, disabled or wrong-typed id becomes the first live default table, the highest rarity ordinal wins and ties are settled by the first eight bytes of the draw as a big-endian integer modulo the tie count, uniform over the tied seats in seat order (`PickTable`). The id goes into `room.Options.Table` and every `MatchView.table`; the draw goes into `room.Options.TableDraw` and the replay record (format version 2), so a replay reproduces the choice without the client ever seeing the bytes. The choice is fixed for the whole match.

Reward bundles (#102): every grant is `reward.Engine.Apply(Grant{Account, Bundle, Source, Reason, Key, ConfigVersion})`. The bundle follows `docs/economy.md` 4 (`reward.ParseBundle` validates id, revision, unique cosmetic and medal ids and that it grants something); the source must be a non-default cosmetics source and the reason a credit reason of section 5. One transaction, under a per-account advisory lock: a repeated key returns the recorded report and writes nothing; the coins go through `wallet.ApplyIn` with the grant key; each cosmetic goes through `inventory.GrantIn` (an unlisted source refuses the whole grant); an owned cosmetic is not granted again and pays `DuplicateCompensationPercent` of its guide price (`GuidePriceCoins[rarity] x GuidePriceTypePercent[type] / 100`, `reward.Config`) as a `duplicate_compensation` entry keyed `<key>:dup:<item>`; medals go to the `Medals` hook (#129) and pass XP to the `Pass` hook (#123), and without a hook, or when it reports no active season, the report records them as skipped or dropped. The report (coins, items, duplicates, medals, XP) is stored in `reward_grants` and published on the `grants` outbox topic for the monitors of #110. `Revoke(account, key, reason, revokeKey)` debits the coins and compensation with the given debit reason, removes the granted items (unequipping them) and medals, and marks the grant; it refuses when the account cannot cover the debit, since a negative balance waits for #106.

Shop (#104): the catalog is `shop.Catalog`, the JSON of `docs/economy/examples/shop.json` (schema 1: offers with the fields of `docs/admin.md` 5.5 and the bundle embedded, plus rotation schedule entries) checked by `shop.Parse` against `HD_SHOP_DAILY_SLOTS`, `HD_SHOP_WEEKLY_SLOTS` and `HD_SHOP_RESET_HOUR_UTC`: a price is coins or a store product, a coin-priced offer grants no coins, a cosmetic offer grants exactly one item once per account, no offer carries a medal, rotation entries start at a period boundary and list at most the slots of their period. Nodes read the catalog from `config_snapshots` (migration 00007: `domain`, `content`, identity `version`): `snapshot.Watcher` polls the newest `shop` row every `HD_CONFIG_POLL` and swaps the parsed catalog in, so a publish (`cmd/config-publish` now, the admin API of #138 later) is live within one poll without a restart; a row that fails validation is logged and the previous version stays; `HD_SHOP_CATALOG` seeds a file as version 0, and without either the shop answers 503 `shop.unavailable`. `GET /shop` answers `{"version","sections":[{"section","ends_at","offers":[...]}]}`, the six sections of `docs/economy.md` 6.1 in order; each offer carries `price_coins` or `product_id`, `reference_price_coins`, `coins`, `cosmetics`, `pass_xp`, `ends_at`, `limit`, `bought`, `owned` with `compensation` per owned item, and `purchasable` with a `reason` (`offer.limit_reached`, `offer.not_eligible`, `offer.owned`, `offer.unsupported` for pass products until #123 and #127). A rotation section ends at its period end and shows the latest schedule entry at or before the period start, so an unscheduled period repeats the previous rotation; an offer outside its window is hidden everywhere. `POST /shop/buy` `{"offer","request_id"}` is one transaction under the account lock: the spend (`shop_purchase`, key `shop:<request_id>:spend`) and the grant through the reward engine (key `shop:<request_id>`, source `shop` with the offer id, config version = snapshot version); a repeated request id answers the stored purchase with `"repeated":true` and writes nothing; 400 `malformed`, `request.invalid`; 404 `offer.unknown`; 409 `offer.unavailable`, `offer.limit_reached`, `offer.owned`, `offer.store_only`, `offer.unsupported`, `item.source_not_listed`; 403 `offer.not_eligible`; 402 `wallet.insufficient`. `POST /shop/begin` `{"offer"}` runs the same checks for a store product and answers `{"offer","product_id","account_token"}`, the account-bound token of `docs/economy.md` 7.5 step 1 (a UUID derived from the account id, `shop.AccountToken`, which the receipt validation of #106 recomputes); 409 `offer.coins_only` for a coin offer. Eligibility is hours since account creation and first purchase only (no `purchase` ledger entry); the limit counts the live grants with the offer as source; a bundle whose every cosmetic is owned is refused unless it also grants coins or pass XP.

Purchases (#106): `POST /shop/complete` `{"offer","platform":"google"|"apple","token"}` finishes the store flow started by `/shop/begin`: `purchase.Google` looks the purchase token up with the Play Developer API (`HD_PLAY_PACKAGE`, a service account JWT from `HD_PLAY_SERVICE_ACCOUNT`, the access token cached until it expires) and `purchase.Apple` verifies the StoreKit 2 signed transaction (an ES256 JWS whose `x5c` chain must end at the embedded Apple Root CA G3 and whose leaf carries the receipt signing extension, bundle `HD_APPLE_BUNDLE_ID`); Play test purchases and App Store sandbox transactions are refused unless `HD_STORE_SANDBOX` is on. The receipt must name the offer's product and carry the account token of `shop.AccountToken`; a mismatch, or a transaction already granted to another account, is refused with 403 and published as evidence on the `purchases` outbox topic for #209; a cancelled or revoked transaction is refused. The grant is one transaction under the account lock: the `purchases` row (migration 00008, unique per platform and transaction id), the offer bundle through the reward engine with reason `purchase` and key `purchase:<platform>:<transaction>`, and on the account's first granted purchase the catalog's `firstPurchase` bundle (reason `first_purchase_bonus`, key `...:first`); a repeated transaction answers the stored result with `"repeated":true`, and only after the commit is a Play purchase consumed (`finished` tells the client whether that happened). A pending purchase (deferred payment) is recorded without a grant and settled when the store's notification reports it purchased. `POST /store/google/notifications?token=<HD_PLAY_NOTIFICATION_TOKEN>` takes the Pub/Sub push of real-time developer notifications and `POST /store/apple/notifications` the App Store Server Notifications V2 `signedPayload`; every notice is processed once (`purchase_notices`): a voided purchase or `REFUND` revokes the grant and the bonus with `refund_revoke` entries that may take the balance below zero (migration 00008 drops the check constraints; a negative balance blocks every spend until earnings cover it), `REFUND_REVERSED` grants the bundle again with `refund_reversal`, and a purchased notice settles a pending purchase. An account with `HD_REFUNDS_BEFORE_PURCHASE_BLOCK` refunds within `HD_REFUND_WINDOW_DAYS` is refused further store purchases (`purchase.blocked`, also shown in the shop view and refused by checkout). Errors: 400 `malformed`, `receipt.malformed`, `receipt.signature`, `receipt.unknown`; 403 `receipt.account`, `receipt.reused`, `purchase.blocked`; 404 `offer.unknown`; 409 `purchase.platform_unavailable`, `receipt.product`, `receipt.cancelled`, `receipt.environment`, `receipt.app`, `offer.coins_only`, `offer.unsupported`; 502 `receipt.store_unavailable`; 503 `shop.unavailable`. A notification with a bad signature or another app's id is answered 401, a sandbox notice in production 200 and ignored, a database failure 500 so the store retries.

Promo codes (#108): `promo.Store` keeps codes in `promo_codes` as HMAC-SHA256 hashes under `HD_PROMO_KEY`, never in clear; `Create` and `Batch` generate codes from the alphabet without `0`, `O`, `1`, `I`, `L` (an admin-chosen code is `multi_use` only), validate the window against `PromoMaxValidityDays`, refuse medals, and start a code as `pending_approval` when its bundle exceeds `PromoCoinsApprovalThreshold` coins or holds a `mythic` item; `Approve` needs a second admin, `Disable` keeps what was granted. `POST /promo/redeem` `{"code"}` normalises the code (case, spaces, dashes), counts the account's attempts in `promo_attempts` (`PromoAttemptsPerHour` → 429 `promo.rate_limited`, `PromoFailedAttemptsBeforeLock` failures → 429 `promo.locked` for `PromoLockMinutes`), then in one transaction under the account lock locks the code row, checks state, window, the per-account uniqueness, the target list and the cap against the redemption count, grants the bundle through the reward engine with source `promo:<campaign>` and key `promo:<id>:<account>`, and writes the `promo_redemptions` row; parallel redemptions queue on the row lock, so the cap is never exceeded. Refusals: 404 `promo.unknown`, 409 `promo.not_active`, `promo.disabled`, `promo.not_started`, `promo.expired`, `promo.exhausted`, `promo.already_redeemed`, `item.source_not_listed`, 403 `promo.not_eligible`, 400 `promo.code_invalid`. Per-device and per-IP limits are #184.

Rating (#112): `rating.Store.Apply` takes a ranked result (match id, mode, the two teams with their offenders, the winner) and, in one transaction, inserts the `rating_results` row (a replay of the same match id changes nothing), locks the four `ratings` rows in account order, resolves the changes with the current `rating` snapshot for the mode and writes the new MMR, rank and LP plus one `rating_changes` row per player. A new account starts at `InitialMmr` in placement: provisional K, no LP, offense penalties summed, and after `PlacementMatches` the first rank is the MMR rank capped at `NewPlayerPlacementCap`; a returning player (a reset rank from the previous season) is placed between the reset rank minus `PlacementMaxDropDivisions` and plus `PlacementMaxClimbDivisions` (#114). `RecalculateApex` orders the Master-and-above rows of a mode by LP, the time the LP was set, wins and account id, gives the first `ChallengerSlots` with at least `ChallengerMinLp` Challenger and the next `GrandmasterSlots` with at least `GrandmasterMinLp` Grandmaster; `cmd/server` runs it per mode at `ApexRecalcHourUtc` under a transaction advisory lock, so several nodes never race. A player entering Master shows Master until the next run and loses the apex tier the moment they drop to Diamond I. Leaderboards are #116; the match end is not wired to `Apply` until the match store is (#50 follow-up).

Seasons (#115): `ranked_seasons` holds the admin seasons (`cmd/ranked-season` until #143), contiguous and non-overlapping by an exclusion constraint. Every ranked result records its season (the one containing the match start) and a `ratings` row carries the season it belongs to. `RunSeasonEnd` polls every `HD_SEASON_POLL`; when a season's end has passed, `CloseSeason` runs once per mode under the row lock of the season: the apex slots are recomputed, every placed row is frozen into `season_results` in the order of `docs/ranking.md` 8.1 with its position and reset rank (`Config.ResetTable` from `ResetTierDrop`, `ResetFloor`, `ResetCeiling` and the optional `seasonResetTable` rows, validated monotone and never above the old rank), the next season is created at the end with `SeasonLengthMonths` when the admin has not created one, and the rows are moved into it unplaced at their reset rank with 0 LP and no wins; MMR is kept. A result of a closed season that arrives late changes MMR only; a result against rows the close has not reached yet answers `rating.season_transition` so the consumer retries.

Leaderboards (#116): `GET /leaderboard/{mode}?board=global&season=<id>` answers the top `LeaderboardTopSize` rows of the board plus the viewer's own row and two neighbours each side (`me` is null while the viewer is unplaced). Every row carries the account id, rank, tier and wins; the client opens the public profile for the rest. The Redis sets are updated by the rating store after every applied result and apex recalculation and rebuilt from `ratings` (open season) or `season_results` (closed season) when missing, so a season's boards freeze at its close; keys carry a 30-day TTL and come back on the next read. Without `HD_REDIS_URL` the route answers 503 `leaderboard.unavailable`. Friends boards are #153.

Country and region boards (#117): `board=country:<CC>` and `board=region:<id>` answer the same shape for the players whose leaderboard country is that country or belongs to that region of `LeaderboardRegions` in the `rating` config (a region id matches `[a-z0-9_]+`, a country belongs to at most one region, 404 `leaderboard.unknown_board` otherwise). The leaderboard country is frozen per season and mode in `ratings.board_country` at the first ranked result played while the account has a country, is copied into `season_results.country` at the close and cleared for the next season, so a country change never moves a player between boards mid-season. The account country comes from `PUT /profile/country` `{"country"}` (ISO 3166-1 alpha-2; 400 `country.invalid`, 409 `country.cooldown` within `HD_COUNTRY_CHANGE_COOLDOWN` of the previous change) or, when `HD_COUNTRY_HEADER` names an edge header, from the connection country at sign-in for accounts without one; `GET /profile/country` answers `{"country","change_available_at"}`.

Every match opens in the loading phase (R-57): the `MatchView` is `MATCH_STATE_LOADING` with the roster (`room.Options.Roster`, filled by the opener from the profile and cosmetics data of #59 and #61), each seat's reported progress and ready flag, and `loading_deadline_unix_ms`. The client sends `LoadingIntent` as it loads and `ready` when the scene is up; the hand is dealt when every seat is ready or when `MatchLoadingSeconds` (`docs/rules.md` section 13, admin config) runs out, whichever comes first. A seat that is not ready and connected at the deal is played by the bot until its player arrives; if nobody arrives within `room.Options.ReconnectGrace` (the opener passes the session grace) the seat counts as left (R-52). The hello of a seated session answers `in_match`, and the client returns to the match instead of the lobby (R-58); `session.Manager.InMatch(account)` backs the `Guard` of the matchmaking pool and the custom lobby, so an account in a running match cannot queue or enter a lobby.

`session.Manager` is the production handler. `Create(account)` issues an opaque 128-bit resume token (login, #57 and #58, calls it); `Seat(token, room, seat)` binds the session to a room, now or later (matchmaking, #48). On connect the token is looked up, a previous live connection of the same session is closed with 1008 `session replaced` (newest device wins, no grace timer for the replaced one), and the `ServerHello` carries the last sequence the room acknowledged, so the client resends anything above it. The first attach joins the seat, every later one reconnects and receives the full `MatchView`. When a connection drops, `ReconnectGrace` starts; if the session has not reconnected when it ends, the seat is left (R-52, the bot plays until the player returns). `ReconnectGraceSeconds` is admin config (`docs/penalties.md` section 8); the code default is 60 s until the owner sets it. Intents from a session without a seat are answered `ILLEGAL_INTENT`. Sessions live in process memory; the Redis store with TTLs (ADR 0005) is #51.

Penalties: at match end the room's `View.Presence` report of each seat goes to `penalties.Record.MatchEnd` with the queue, match id and config version; the returned `Notice` is what the player sees. `Record.QueueDelay` becomes the `SearchFrom` offset of the next `matchmaking.Entry`, `Record.Banned` gates ranked enqueue (ban or review), and `penalties.Results` tells the rating and reward engines how to treat each seat. `penalties.DefaultConfig` holds placeholder numbers until the admin panel publishes the real ones; the record is kept in memory by its caller until the data layer (#50, #55) stores it.

## Load test

```
cd server
go run ./cmd/loadbot serve -addr :8080                 # on the node under test, same HD_* variables as cmd/server
go run ./cmd/loadbot run -target ws://node:8080/ws -rooms 10000 -2v2 50 -ramp 5m -hold 30m -out report.json
go run ./cmd/loadbot local -rooms 1000 -hold 2m       # one process, developer machine
```

`serve` is the game server with the load-mode handler instead of the session manager: any client whose token is `<room>/<mode>/<seat>` is seated, a room is opened on its first token and a second connection with the same token resumes the seat with the acked sequence it sends. It is never deployed to a player-facing environment. `run` keeps `-rooms` rooms active (a finished match is replaced at once), seats every player with a `botclient`, waits `-think-min` to `-think-max` before the first action of each turn and `-think-follow` before a further draw or placement in the same turn (R-49 times the whole turn), drops each connection `-drops` times per minute on average and resumes it, and timestamps every intent from send to the first broadcast that acknowledges it. The report has mean, p50, p95, p99 and max overall, the steady state after `-warmup`, every `-window`, drops, reconnects, rejected intents, dial and read failures, bytes per intent and, in `local` mode, heap samples. The exit code is 1 when the steady-state p99 or any window after the warm-up is not under `-budget` (100 ms), the error rate is not under 0.1% or the heap grew more than 5% in the steady state. A 12-hour soak is `-hold 12h`; the full target is `-rooms 10000` from a host with the file descriptor limit raised above 40,000.

## Match results

`internal/matchstore` is the only writer of match rows. A room calls `Begin` when the match starts (one `matches` row and one `match_participants` row per seat, bots with a null account) and `Finish` once when it ends. `Finish` locks the match row, refuses it when `ended_at` is already set (`ErrAlreadyFinished`), and in the same transaction stores the final scores, winner, hands played, the replay bytes, per-seat results, the `match_events` log and the outbox messages built by `MatchMessages(kind, key, payload)`: ranked matches feed `rating`, `xp`, `missions` and `economy`, casual matches skip `rating`, custom matches only feed `missions`. `Relay.Run` polls the outbox and hands each pending row to a `Publisher`; a failed publish increments `attempts` and keeps the row pending, so delivery is at least once and consumers deduplicate on `(topic, key)`. Tests run against the same PostgreSQL as `internal/db`.

## Cluster

With `HD_REDIS_URL` set the node heartbeats into Redis, `session.Manager` claims a route for every seated session, and the gateway handler is `cluster.Relay`: a hello whose token is unknown locally is looked up in the routes and, when another live node owns it, relayed over the cluster network to that node's `HD_NODE_ADDR` with the `X-HD-Relay` header; frames are piped both ways until either side closes. A draining node refuses public WebSockets but accepts relayed ones, so a player who drops during a deploy finishes the match on the old pod. A relayed hello is never relayed again. When the owning node's heartbeat has expired the route is dropped and the client gets `UNAUTHENTICATED`; the match is lost without result or penalty (ADR 0011, node loss).

`GET /loadz` returns `{"load": {...}, "node": {...}, "cluster": {"nodes", "rooms", "connections", "capacity", "utilization", "advice"}}`; `advice` is `out`, `in` or `hold` by `HD_SCALE_OUT_AT` and `HD_SCALE_IN_AT`. Without Redis only `load` is present. Integration tests in `internal/cluster` and `internal/app` run against a real Redis 7: `go test ./internal/cluster/ ./internal/app/` starts `redis:7-alpine` through testcontainers on the local Docker or connects to `HD_TEST_REDIS_URL` when set; `-short` skips them.
