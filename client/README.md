# client

Unity 6 LTS game client (URP Universal Renderer with 2D sprites, kept from the superseded ADR 0009; C#, Addressables). It renders state and sends player intents only; the server decides every rule, score and reward.

## Editor

Unity `6000.3.27f1` (Unity 6.3 LTS), pinned in `ProjectSettings/ProjectVersion.txt`. Install it with Unity Hub together with Android Build Support (OpenJDK, Android SDK & NDK Tools). An upgrade is its own PR with a measurement (ADR 0001).

## Measuring the empty build

`Scenes/Boot.unity` holds an orthographic camera and `FrameTimingSampler`. The `BootSceneSmokeTests` PlayMode smoke test checks that it is the first build scene, loads it, runs 60 frames and fails on any error or exception logged meanwhile. The sampler measures at the frame rate `GraphicsBoot` set (`docs/performance.md` 1.2; the highest refresh rate when none is set) and logs every 1200 frames:

```
FrameTiming target=<Hz> frames=1200 workP50=<ms>ms workP95=<ms>ms missedVsync=<percent>% gcFrames=<n> gcMax=<bytes>B gcCollections=<n> batchesMax=<n>
```

Work time is `max(cpuMainThreadFrameTime, cpuRenderThreadFrameTime, gpuFrameTime)` (`FrameWindow.WorkMs`), shared with `GraphicsProbe` and the benches; a missed vsync is a presented interval longer than 1.5 refresh periods (`docs/performance.md` 2). Read it with `adb logcat -s Unity`.

`gcFrames` counts frames whose `ProfilerRecorder` "GC Allocated In Frame" was above 0, `gcMax` is the largest of them, `gcCollections` is the `GC.CollectionCount(0)` delta and `batchesMax` the largest "Batches Count" (`docs/performance.md` 3). A counter the player does not expose prints `n/a`; the Profiler counters need a development build. The frame that writes the log line allocates that line, so its GC value is not counted. `FrameWindow` holds the window and the `FrameWindowTests` EditMode tests cover it.

In a development build `FrameStatsOverlay`, on the same object as the sampler in `Scenes/Boot.unity`, shows the sampler's live window of the last 60 frames in the top-left of the safe area: work time p95 in ms, missed vsyncs in percent, frames that allocated (in the danger colour when above 0) and the most batches. It refreshes once per window, takes its numbers from string tables filled at start, so showing them allocates nothing (`FrameStatsOverlayTests`), and removes itself in a release build, so store screenshots never show it.

Size: the `Release build` workflow below; the Build Report (`Library/LastBuild.buildreport`) of a local release build gives the content breakdown.

## App flow

`Game/AppFlow` holds which part of the app is shown: `Boot`, `Login`, `Lobby`, `Match`, `UpdateRequired` or `Maintenance`. It is plain C#, fed by server messages, and raises `Changed` once per new state.

- `SignInNeeded` (no session or `UNAUTHENTICATED`) goes to `Login`, except while an update is required.
- An accepted `ServerHello` goes to `Match` when `in_match` is set (R-58), otherwise to `Lobby`. `UPDATE_REQUIRED` and `MAINTENANCE` go to their screens (ADR 0004). An unknown status changes nothing.
- A `MatchView` that is not finished takes the lobby into the match, so a match found by the queue or a friend room starts the same way.
- `LeaveMatch` returns to the lobby only after the match is finished.

`Game/MaintenanceScreen` is the model of the maintenance screen. `NetBoot` builds it with its dial and feeds it every `ServerHello`. A `MAINTENANCE` hello makes it `Active` with the `maintenance_ends_unix_ms` the server sent as `EndsUnixMs` (0 when the server sent none, `HasEnd` false); an accepted or `UPDATE_REQUIRED` hello closes it, and an unknown status changes nothing. The server closes the connection after a maintenance hello and nothing reopens it on its own, so `Retry` dials again; it is refused while a retry waits for the server's answer (`Checking`). `Tick`, called every frame by `NetBoot`, retries once when the end time passes, counted on the server time of the hello, never the device clock; a later hello with the same end time does not retry again, only a moved end time or a tap does (`docs/anti-cheat.md` 5.2: the end time is shown, not enforced). `Changed` is raised once per change of what the screen shows. Ticking before the end allocates nothing. `MaintenanceScreenTests` cover it.

`Game/StoreLink.Of(platform, applicationId)` is the store page the update screen opens: on Android the Play page of `Application.identifier`, elsewhere none until the App Store app id is known. `StoreLinkTests` cover it. The update and maintenance views and their texts (`docs/launch-runbook.md` 8.2) are #848.

`Game/AppBoot` is the composition root: before the first scene it creates the one `AppFlow` (`AppBoot.Flow`) and follows its changes. Entering `Match` calls `GraphicsBoot.FrameRate.SetInMatch(true)` and `ContentBoot.Catalog.SetInMatch(true)`; any other state calls both with `false`, so the chosen frame rate applies and new catalogs wait from the moment the match is shown until the app leaves it, result screen included. In the editor there is no catalog and only the frame rate follows. Each change logs one `App state=<state>` line.

`AppBoot.Listen(session, flow, catalog, strings, playHaptic)` feeds the flow from a `Session`: every `ServerHello` goes to `Hello`, and the `MatchState` of every `MatchView` goes to `View`. It also keeps one `HapticCues` for the session: every `ServerHello` starts a new connection on it, and every `MatchView` hands its cue to `playHaptic`, so the first view after a reconnect plays nothing. After an accepted hello it calls `Announce(catalog_version, content_base_url)` on the catalog (`docs/content-delivery.md` CD-5); the flow takes the hello first, so a hello into a running match holds the new catalog until the match is left. A null catalog (the editor) is skipped. Passing a `MatchView` on allocates nothing. `NetBoot` calls it once.

`Game/NetBoot` builds the network side after the first scene loads, once the boot classes above exist:
- `Net/ServerEndpoint.Load` reads `Resources/ServerEndpoint.json`, which `Editor/ReleaseBuild` writes from `-serverUrl` and `-httpTimeoutSeconds` (`docs/environments.md` 2.5). The editor uses `http://localhost:8080` without a timeout. A player built without both logs `Net no server endpoint` and builds nothing.
- One `UnityHttpTransport(serverUrl, httpTimeoutSeconds)` serves `AuthSession(transport, identity, store)` and `ApiClient(transport, auth)`. `NetBoot.Auth` and `NetBoot.Api` expose them.
- One `Connection` dials `<serverUrl>/ws` (`wss` for `https`) with a new `WebSocketTransport` per dial and `Time.realtimeSinceStartupAsDouble` as its clock. A hidden driver calls `Tick` every frame.
- Each dial sends a new `ClientHello`: `Application.version`, the platform, `SystemInfo.operatingSystem` and `deviceModel`, the access token of `AuthSession` and the device time in ms. `build_hash` stays empty: no document defines it, and the build allowlist is off by default (`proto/README.md`, Gateway limits). `integrity` is filled by `SessionStartProof` (below). `DeviceRiskProbe.Collect` fills `Session.DeviceRiskSignals` once. `NetBoot` sets `Session.CollectHookSignals` to `DeviceRiskProbe.CollectHooks`, so `Session.HookSignals` is collected again before each hello, and a debugger attached after start shows on the next dial. Every hello carries both.
- `NetBoot.Integrity` is an `IntegrityProofs` on `NetBoot.Api` with `NoDeviceAttestor` until the native attestors exist, so no device asks for a nonce yet. A `SessionStartProof` on it runs every new connection: the dial that is not a `Rejoin` first asks for a `session_start` proof, then calls `Connection.Start`, and each hello gets the proof attached until a hello is accepted. It reads every `ServerHello`, and every `Error` other than `UNAUTHENTICATED`: an `INTEGRITY_FAILED` after a hello without a proof asks for one proof and starts again only if one arrived. The `SessionStartProofTests` EditMode tests cover it.
- `AppBoot.Listen` gets `connection.Session`, `AppBoot.Flow`, `ContentBoot.Catalog`, `LanguageBoot.Strings`, `LanguageBoot.Bundles`, `ContentBoot.CosmeticsUpdater`, `Haptics.Play` and `AudioBoot.PlayMatch`.
- `NetBoot.Queue` is a `MatchQueue` following the session and the flow. `NetBoot.Lobby` is the `LobbyCommands`, and `NetBoot.Room` is a `FriendRoom` that reads every `LobbyState` with the signed-in account id. `FriendLobbyBoot.Start` then builds `FriendLobbyBoot.Link`, the friend lobby models on that room (below).
- The screens load through `NetBoot.Shop`, `Pass`, `Missions`, `Inventory`, `Medals` and `Profile`, the six loaders built once on `NetBoot.Api`.
- `NetBoot.LobbyScreen` is the lobby model (#74): a `LobbyHeader` and a `LobbyPlay` that asks `NetBoot.Integrity` (an `IntegrityProofs` on `NetBoot.Api` with `NoDeviceAttestor`) for the card's proof and joins through `NetBoot.Queue`. `NetBoot.LobbyHeaderLoader` fills that header each time `AppBoot.Flow` enters `Lobby`: after an accepted hello, a finished match or leaving a friend room, through `NetBoot.ReloadHeader`. A hello that keeps the lobby loads nothing, nor does a load already in flight. An outcome other than `Loaded` is logged as `Lobby header outcome=<outcome>`; what the header shows then and a retry policy are not decided. The `LobbyWiringTests` EditMode tests cover it.

`Game/NetStart` is the start order, plain C#:
- `Begin`: with a stored session, `AuthSession.Resume` and then the dial; without one, `SignInNeeded`.
- `Unauthenticated`: the `Connection` has stopped. Another `Resume` runs, then the dial again (a redial on the same `Connection`).
- After a `Resume`, `SignedIn` dials and `SignInRequired` sends the flow to `SignInNeeded`. Any other outcome is logged as `Net resume outcome=<outcome>`, and the app stays where it is; a retry policy for `Offline`, `Unavailable` and `RateLimited` is not decided.

The `NetStartTests` and `ServerEndpointTests` EditMode tests cover the start order, the endpoint rules and the hello fields. The `Login` state is driven by `NetBoot.Login`, a `LoginScreen` (see Sign-in).

The `AppFlowTests` EditMode tests cover every transition, the `AppBootTests` EditMode tests which states count as in a match and that hellos and views read by a `Session` reach the flow and the catalog, and the `AppBootTests` PlayMode test that the running flow moves the frame rate in and out of a match. Scenes and DI beyond this root are not built yet.

`Game/StartupMarker` writes the cold start marker of `docs/performance.md` section 3. Built with the `AppFlow`, a clock and a log, it logs one `Startup state=<first state after Boot> ms=<seconds since startup x 1000>` line at the first state change and then stops listening. `AppBoot` creates it with `AppBoot.Flow`, `Time.realtimeSinceStartupAsDouble` and `Debug.Log`. A run that reaches the lobby directly logs `state=Lobby`; a run that shows sign-in, an update, maintenance or a running match first logs that state instead, so it is not counted as a lobby start. Right after it, it logs the startup chain kept by `Core/Diagnostics/StartupPhases.App` as one `Startup phases <phase>=<ms> ...` line, the phases in the order they ended and the first screen last, such as `Startup phases assemblies=<ms> GraphicsBoot=<ms> ... AudioBoot=<ms> scene=<ms> Login=<ms>`. `assemblies` is marked by `AppBoot` once the scripts are loaded (`AfterAssembliesLoaded`), every boot that runs before the first scene marks its own name when its work is done, and `AppBoot` marks `scene` when the first scene has loaded. The boots run in an order Unity does not fix, so a boot's cost is its value minus the one before it on the line. The network side follows: `NetBoot` marks its own name once it is composed, and its `Game/NetStartPhases` marks `resume` when the stored sign-in resumed and the first dial is asked for, `proof` when the session start proof arrived (or none was needed) and `Connection.Start` runs, and `dial` on the first frame the socket of that dial is open; a retried dial is watched until one opens. The first screen that closes the line is the server hello, so the time from `dial` to it is the hello round trip. Each step is marked only the first time, a run that shows sign-in first closes the line before any network step, and marks after the first screen are dropped. The `StartupMarkerTests`, `StartupPhasesTests` and `NetStartPhasesTests` EditMode tests cover both lines, and `ArchitectureTests` fails a boot before the first scene that does not mark its phase.

## Lobby queue

`Game/Lobby/MatchQueue` is the model behind the lobby's play button (#74, `docs/matchmaking.md` section 4); the server decides who is matched, when and whether an entry is accepted. `TryJoin(session, mode, kind, integrity)` sends one `JoinQueueIntent` with a mode and a queue the protocol names (`MODE_1V1` or `MODE_2V2`, `QUEUE_KIND_RANKED` or `QUEUE_KIND_CASUAL`) and the device proof (`docs/anti-cheat.md` 5.1, match start); it sends nothing before an accepted hello, while an earlier intent still waits for its `QueueState`, or after `MATCH_FOUND`. A join while searching is sent, and the server replaces the entry. `TryLeave` sends one `LeaveQueueIntent` while searching or while the join is unanswered, and no second one until the replies arrive. Every `QueueState` except `MATCH_FOUND` answers one intent, in order.

`Read(QueueState)` shows what the server sent: `Searching` with the mode, the queue, the join time and the time the search starts; `Idle` after `LEFT`; `MatchFound`, kept until the app returns to the lobby; `Refused` with the reason and the ban end. An unknown status answers its intent and changes nothing. `RefusalKey` names the game string of the reason, `lobby.queue.refused.<reason>` (`in_match`, `matchmaking_ban`, `ranked_closed`, `unavailable`, `integrity_failed`, `integrity_unavailable`, `ranked_ban`), and `notice.generic` for any other. A `RANKED_BAN` refuses ranked entries only, casual stays open (owner decision 1 of #186). `BanReason` is the `ban_reason` of a matchmaking or ranked ban, and `BanReasonKey` names its text, `ban.reason.<category>` through `BanReasonKeys.Of`, `ban.reason.other` for an unknown category and none without a reason or outside `Refused`; the countdown to its end is `SecondsUntilBanEnds` as for any ban. `Appeal` is the appeal grant of the refusal (Appeals), none outside `Refused`. `SecondsSearching`, `SecondsUntilSearch` (a penalty queue delay, `docs/penalties.md`) and `SecondsUntilBanEnds` count from `ServerClock`, never the device clock, and are 0 when the clock is not synced or the server sent no time; a ban without an end (under review) counts nothing. `Changed` is raised after each state read. `Follow(session, flow)` reads every `QueueState` of the `Session` and resets the model on every `ServerHello`, because the server drops the entry when a connection closes, and whenever the `AppFlow` enters `Lobby`. Reading a state allocates nothing. Of the refusal keys only `ranked_ban` has built-in texts yet; every `ban.reason.*` key has them. The `MatchQueueTests` EditMode tests cover the intents, every reply, the refusal and ban reason keys, the server-time counts, following a session and the flow, and 0 B reads.

## Lobby screen

`Game/Lobby` also holds the plain C# model the lobby screen reads (#74), so its views only bind and never decide.

- **Mode cards.** `PlayModes` lists the four queues of `docs/matchmaking.md` section 1 as cards: ranked 1v1, ranked 2v2, casual 1v1 and casual 2v2, each with its `IntegrityPurpose` (`ranked_match` or `casual_match`). The friend room is its own entry (`Game/FriendLobby`).
- **Play.** `LobbyPlay.Play(session, card)` asks for the device proof of the card's queue (`Net/Integrity/IntegrityProofs.Request`, passed in as a delegate) and sends the join with it through `MatchQueue.TryJoin` once the proof arrives; no proof (no attestor, no nonce) still joins and the server's policy decides (`docs/anti-cheat.md` 5.1). A tap while a proof is awaited, while an intent waits for its `QueueState` or after `MATCH_FOUND` starts nothing. `Cancel` drops an awaited proof, so a late proof never joins, or sends the leave. `StateOf(card)` is `Starting` for the card being proved or joined, `Searching` for the card whose queue the server searches, `Locked` for every card while another one starts, a leave is unanswered or a match was found, and `Ready` otherwise; a tap on another card while searching moves the entry, as the server replaces it.
- **Training.** The training card is not a queue (owner decision of 2026-11-21, #852): `LobbyTraining.Start` opens the bot game of #89 through `Game/Training/ITrainingGame.TryStart` and never sends a queue intent. Its `State` is `Locked` while a card is proved, an intent waits for its `QueueState`, the server searches or a match was found, and `Ready` otherwise, a refusal included; a running search is never left by training, the player cancels it first. It changes only with what raises `LobbyPlay.Changed`, so a view reads it on the `Play` part. The bot game behind `ITrainingGame` does not exist yet (#89), so `NetBoot` builds no `LobbyTraining`. The `LobbyTrainingTests` EditMode tests cover it.
- **Header.** `LobbyHeader` shows the coins, crystals and level as the server sent them and raises `Changed` only when a value differs. `LobbyHeaderLoader.Load` sends `GET /wallet` and `GET /profile/me` together, shows each part as it reads, and answers once with the first failure (`Offline`, `SignInRequired`, `RateLimited`, `SetupRequired` for a profile without a nickname, `Failed`) or `Loaded`. A second load while one is in flight sends nothing. The level is the current pass season's level (`docs/privacy.md` D-10).
- **Idle cost.** `LobbyScreen.Tick(clock, now)` returns the parts that changed since the last tick: `Header`, `Play` and `Countdown`. The countdown is the whole seconds of the search (`Searching`), of a penalty delay before the search starts (`SearchStartsIn`) or of a matchmaking ban (`BanEndsIn`), all from `ServerClock`, so it changes at most once a second. A view sets its text only for a returned part, so an idle lobby touches no `Graphic` and rebuilds no canvas; the first tick, and the one after `ShowAll`, returns every part. Ticking and reading the card states allocate nothing (`LobbyTests`).

`Balances.TryRead` reads a `GET /wallet` body for both the shop and the lobby header. The `LobbyTests` EditMode tests cover the cards, the play and cancel flow, stale proofs, the header and its loader, and the countdowns.

## Network frames

`Net` reads and writes the `Envelope` frames of `proto/README.md` without the generated `Envelope` parser, which allocates a new payload message on every parse. `FrameReader.TryRead` walks the frame by hand and returns a `Frame` (a `ref struct`): the header (`protocol_version`, `sequence`, `acked_sequence`, `session_nonce`), the payload case and the payload bytes as a span over the frame. The caller merges those bytes into a message it keeps (`message.MergeFrom(frame.PayloadBytes)`). A field it does not know, including a payload number newer than this client, is skipped, so the payload reads as `None`; a truncated or malformed frame returns `false`. `FrameWriter` writes a header and one intent into its own buffer and returns a span over it, valid until the next write; an intent kept and changed in place is sent without allocating. The `FrameCodecTests` EditMode tests read every golden frame in `proto/testdata/frames` like the generated parser does, write every client golden frame byte for byte, refuse malformed frames, and check that reading a `MatchView` frame and writing a reused intent allocate nothing.

`MatchSnapshot.TryRead` decodes a `MatchView` payload by hand, including each seat's `disconnected` and `consecutive_timeouts`, into arrays it keeps, because the generated parser allocates every tile, seat and legal move. Lists come back as `ReadOnlySpan`s of structs (`TileFace`, `SeatState`, `OrientedTileFace`, `OpenEndValue`, `LegalMoveValue`), sized by the set: 28 tiles (`docs/rules.md` R-1), 4 seats, 4 open ends, 112 legal moves; more is refused. A field absent from the frame reads as its default, and `HasSpinner`, `HasForcedOpening` and `HasLastResult` tell an absent message from a zero one. The roster and table follow `proto/README.md`: a view without them keeps the ones already read, and they are the only parts that allocate, once per connection. A malformed view returns `false` and leaves the snapshot partly written, so the caller drops it. The `MatchSnapshotTests` EditMode tests compare every golden `MatchView` and one that sets every field with the generated parser, and check roster keeping, shrinking lists, the size limit, unknown fields, truncation and that a view without a roster allocates nothing.

`Session` speaks the protocol over an `IFrameTransport`, which sends one frame and hands back received frames on the main thread. `Hello` takes the transport of the current connection and sends the `ClientHello` with the last acknowledged sequence. An accepted `ServerHello` gives the `session_nonce` that `Send` stamps on every later intent. `PlaceTileIntent`, `PassIntent`, `DrawIntent` and `EndTurnIntent` take the next sequence; loading, emoji, quick message and queue intents carry none. The counter never falls behind the server's `acked_sequence`, so a resumed session goes on after the last accepted intent instead of being dropped as stale. `Poll` reads every waiting frame: a `MatchView` goes into the `MatchSnapshot` the session keeps, and `ServerHello`, `Error`, `QueueState`, `EmojiShown`, `QuickMessageShown`, `LobbyState`, `LobbyRelay` and `LobbyInvite` are raised as events with the generated message. A frame that does not read, carries a newer `protocol_version` or a payload only a client sends breaks the session: it stops reading and refuses intents until the next hello. Room frames arrive without `protocol_version`, so a missing one is read. The `SessionTests` EditMode tests send the golden hellos byte for byte, number intents, resume after an acked sequence, route every server payload, break on bad frames, and check that polling a `MatchView` without a roster and sending a reused turn intent allocate nothing. Every allocation test runs its step once before measuring, so first-call setup is not counted.

`WebSocketTransport` is the `IFrameTransport` over `System.Net.WebSockets.ClientWebSocket`. `Connect` dials once on a background receive thread; a send thread starts when the socket opens. Both rings are preallocated: `Send` copies the frame into one of 8 send slots of `Session.MaxSentFrameBytes`, so frames sent while connecting go out in order once the socket opens, and the receive thread fills one of 8 receive slots of 16 KiB. `TryReceive` returns the oldest frame as a span over its slot, valid until the next call; a full receive ring stops reading the socket until the main thread polls again. Neither call allocates on the main thread. A close from the server, a text frame, a frame over 16 KiB, a full send queue, a failed connect or `Dispose` moves `State` to `Closed` with `CloseStatus` and `CloseDescription`; frames received before the close can still be read. The background threads still allocate inside `ClientWebSocket`, a few times per frame. The `WebSocketTransportTests` EditMode tests run it against a loopback WebSocket server written over `TcpListener`.

`Connection` keeps one `Session` alive across sockets; the app calls `Tick` once per frame. `Start` dials, sends the hello from the app's `ClientHello` provider and waits in `Connecting`; an accepted hello moves it to `Online`. A socket that closes, or a session that breaks, is dropped after the frames already received are read, and the next socket is dialled on this schedule: at once, then after 0.5, 1, 2 and 4 s, then every 5 s, each delay spread by ±20 % so a server restart does not bring every player back in the same instant. The server keeps a dropped seat for `HD_RECONNECT_GRACE` (60 s), about 14 attempts. An accepted hello starts the schedule again, so a close after `MATCH_FOUND` on another node is redialled at once. The resume hello carries the last acked sequence. `UPDATE_REQUIRED`, `MAINTENANCE`, `UNAUTHENTICATED`, `INTEGRITY_FAILED` and `UNSUPPORTED_PROTOCOL` stop the connection: dialling again cannot fix them, and the app shows the matching screen and calls `Start` when it can go on.

`ServerClock` maps the local monotonic clock (`Time.realtimeSinceStartupAsDouble`, not the device clock the player can change) to server time from the hello's `server_time_unix_ms`, taken as the middle of the hello round trip; the server's sign-in work inside that round trip makes it a little late, which is well under a second and fine for turn and loading deadlines. `RoundTrip` times each turn intent from `Send` to the first frame whose `acked_sequence` covers it, as read by `Tick`, so a sample includes up to one frame of polling. An intent the server answers with an `Error` naming its sequence is not timed and stops waiting for its ack, whatever the code: `ILLEGAL_INTENT` for a refused move, and `RATE_LIMITED` or `REPLAY_REJECTED` for one the gateway dropped, so a dropped intent never shows `Weak` or skews the next sample. `SmoothedMs` follows the samples with a gain of 1/8, the smoothing TCP uses for its round-trip estimate (RFC 6298). The `ConnectionTests` EditMode tests drive it with a fake socket and clock: the schedule and its jitter, reset on resume, the resume hello, frames read before a close, every stopping answer, clock mapping, round-trip samples, that a rejected or dropped intent is neither timed nor waited on, and that a quiet `Tick` allocates nothing.

`ConnectionNotices` decides what the connection UX of #87 shows, from the `Connection` and the latest `MatchSnapshot`. `Network` is `Reconnecting` while a session that was online waits or dials again (the first dial is the boot screen's, not a notice), and `Weak` while online when the smoothed round trip is over 300 ms or a turn intent has waited more than 2 s for its ack (thresholds chosen by the owner). `Seat` is `Dropped` for a seat whose player lost the connection but still holds the seat, and `BotPlaying` for a human seat the bot plays after the AFK mark or the reconnect grace; a bot from the roster has no notice. `OneTimeoutFromBot` is true when the player's own next timeout would hand the seat to the bot (R-51), from the seat's `consecutive_timeouts` and the view's `afk_consecutive_timeouts`, and false once the match has finished, as no timeout follows. `CanTakeBack` is true while the player's own seat is played by the bot and the match has not finished: the player may take back control by reconnecting (R-51, R-52, R-58). `Connection.Rejoin` does that for a session that is still online, which is the case after the AFK mark: it drops the socket and dials again at once with the resume hello, so `Network` shows `Reconnecting` until the hello is accepted and the server hands the seat back. It does nothing in any other state, where the schedule above already redials. The screens that show them come with the match scene. The `ConnectionNoticesTests` and `ConnectionTests` EditMode tests cover every notice, both thresholds, the take-back offer and the rejoin.

`Game/Match/ConnectionNoticeKeys` names the game string key of each notice and of the take-back banner; their `az` and `en` texts are in the built-in bundle and listed in `docs/ui-motion.md` (Connection notices). `Game/Match/TakeBackBanner` is the banner's logic: `Read` takes each new `MatchSnapshot` and shows the banner while `CanTakeBack` holds, and `Tap` calls `Connection.Rejoin` once, ignoring further taps until the next view is read; a tap the connection refuses because it is not online is not counted. Only the banner calls it, never a tap on the hand. A weak connection changes no effect or quality level. The banner's view comes with the match scene (#78). The `ConnectionNoticeKeysTests` and `TakeBackBannerTests` EditMode tests cover the keys in the shipped bundle, when the banner shows, the single rejoin and that reading a view allocates nothing.

`Game/Match/SeatBadges` places each seat's `Seat` notice on the table side of that seat, with the same seat-to-side mapping as `SeatAvatars` (`SeatOrder.IsIn`, `TableSides.Of`). `Read` takes each new `MatchSnapshot` and returns whether any side's badge changed, so the seat views set their text only then; `At` gives a side's notice, whose string key is `ConnectionNoticeKeys.Of`. The badge views come with the seat art and the match scene (#78). The `SeatBadgesTests` EditMode tests cover the side of each seat in 1v1 and 2v2, a viewer without a seat, roster bots, seats outside the mode, change reporting and that reading a view allocates nothing.

`Game/Match/MatchNotices` holds everything the match screen shows about the connection, so its views read one place. `Tick` takes the `Connection` each frame and returns whether the `Network` notice changed; `Read` takes each new `MatchSnapshot`, feeds its `SeatBadges` and `TakeBackBanner`, sets `AfkWarning` from `OneTimeoutFromBot`, and returns whether any badge, the warning or the banner changed. The views set their text only when a call returns true. The AFK warning and the take-back banner never show together: one needs the player in control of the own seat, the other the bot. `MatchScreen` holds one as `Notices`, reads it on every view and ticks it every frame, and calls `IMatchHud.ShowNotices` only when a call returns true; the HUD views that show it come with the match scene (#78). The `MatchNoticesTests` EditMode tests cover change reporting for views and frames, the warning giving way to the banner, the finished match and that a frame allocates nothing.

## Shop and wallet

`UI/Shop` turns server replies into what the shop shows, without computing anything (`docs/economy.md` 3.4, 6.1). `WalletReply`, `ShopReply` and `PurchaseReply` read `GET /wallet`, `GET /shop` and `POST /shop/buy` with `JsonUtility`. `Balances` keeps coins and crystals apart and takes the new balance of a purchase's `currency` from the reply. `ChestCard` copies a `chest` offer's pool, owned items, odds (`[{"rarity","percent"}]`), opens left to the pity, price and refusal reason as sent. `ChestReveal` holds only the granted item, its rarity key and the opens left to the pity, so a reveal can show nothing but the result: no reels, wheels, slot sounds or near-miss effects (`docs/localization.md` section 6). Names are keys: `currency.coin.name`, `currency.crystal.name`, `rarity.<id>.name`.

`Game/Shop` sends the purchase intent of an offer priced in coins or crystals (#105, `docs/economy.md` 3 and 5); the server takes the price, checks ownership, limit and balance and spends. `ShopBuyer.Buy` posts `{"offer","request_id"}` to `POST /shop/buy` through `ApiClient`, so it is signed with the request MAC, and refuses a second purchase while one is in flight. The request id is 32 random hex characters made per intent and kept in memory only. It is reused when the same offer is bought again after an answer that does not settle the intent (no response, rate limit, a server error or an unreadable success), so a retry of a purchase the server may already have made only repeats the earlier answer (V-8) and never spends twice; a purchase or a refusal settles it, and another offer always gets a new id. `ShopBuyResult.From` turns the reply into one `ShopBuyOutcome`: a purchase keeps the `PurchaseReply` as sent for `Balances.After` and `ChestReveal`, and `Duplicates` (owned cosmetic id to the coins paid as duplicate compensation, `grant.duplicates`, `docs/economy.md` 2.7) read with `GrantDuplicates`; each refusal of the shop has its own key `shop.buy.<reason>` (`insufficient` for `wallet.insufficient`, `owned`, `limit_reached`, `not_eligible`, `unavailable`, `unknown`, `unsupported`, `store_only`, `in_game_only`, `purchase_blocked` for `purchase.blocked`, the refund block of `docs/economy.md` 9, and `purchases_disabled` for the 503 `purchases.disabled` of the purchase kill switch, `docs/anti-cheat.md` 5.2, which does not settle the intent); the limiter's `rate_limited` is `shop.buy.rate_limited`, no response is `shop.buy.offline`, a purchase is `shop.buy.bought`; every other reply, including a reason a newer server adds, is `notice.generic`. A lost session has no message key and goes back to sign-in. The built-in bundle holds the `en` and `az` text of every key. Store products go through `POST /shop/begin` and a store receipt instead (`ShopPurchase` below). The `ShopBuyTests` EditMode tests cover the intent body, every reply, the single request in flight, when a request id is reused and the shipped texts of every shop buy, load and section key.

`Game/Shop/ShopShowcase` is the showcase model of `GET /shop` (`ShopShowcase.Path`, #105, `docs/economy.md` 6). `ShopShowcase.TryRead` reads the reply body into `ShopSection`s and `OfferCard`s in the server's order. A section the client has no title key for (one a newer server adds) and a section without offers are left out; every other section keeps its place. Each section has a title key `shop.section.<section>.title` (`ShopSectionKeys`, with built-in `en` and `az` texts). An `OfferCard` copies what the server sent: id, kind, name key, the price (`OfferPrice`: coins or crystals as a `Balance`, or the store `product_id` with `InStore`), the struck-through reference price in the price's currency when sent, the coins, crystals, pass XP and cosmetics it grants, the owned items, `limit` and `bought`, `purchasable` and the refusal reason with its `shop.buy.<reason>` key, and the `ChestCard` of a chest. Nothing is computed or checked against a price on the client; a store product's localized price comes from the billing SDK, which is not on the client yet. A reply whose offer has no id or name key, not exactly one of `price_coins`, `price_crystals` and `product_id`, a negative price or an unreadable `ends_at` is refused whole. Countdowns use only the connection's `ServerClock`: a section counts down to its `ends_at` (the rotation period end), a card to the earlier of its own `ends_at` (the window end) and its section's, and `TrySecondsLeft` answers nothing before the clock syncs or when there is no end (`docs/economy.md` 6.3, NT-6). The tick allocates nothing. The duplicate compensation of each offer (`compensation`, owned item id to coins, `docs/economy.md` 2.7 and 6.2) is a JSON map, which `JsonUtility` cannot read: `TryRead` reads it from the same body with `Net/JsonMap` into `OfferReply.compensation`, offer by offer in the server's order, and the card shows it as `CompensationCoins` and `TryCompensationCoins(item)`, for display only. A missing or `null` map is none; a map that is not an object, an amount that is not a whole number of at least 0, or an item that is not in the offer's `owned` refuses the whole reply. `ServerClock.TryReadUnixMs` reads the RFC 3339 times of HTTP replies for the shop and `PassStanding`. The `ShopShowcaseTests` EditMode tests cover the order, title keys, prices, owned and limit state, compensation, refusals and the countdowns.

`Game/Shop/ShopCheckout` is the preview and confirm step of a purchase (#105). A tap on a card opens its preview (`Open`, the `OfferCard` as the server sent it: price, reference price, contents, owned items with their compensation, the refusal key), and a tap on confirm (`Confirm`) sends it, so a purchase takes two taps. An offer priced in coins or crystals goes through `ShopBuyer` (`POST /shop/buy`); an offer with a store product id, crystal packs, the starter offer and the premium pass products alike (`docs/economy.md` 6.1, 7.2: a `kind: pass` offer is a shop offer), goes through `ShopPurchase` (`/shop/begin`, the store, `/shop/complete`) and never through the in-game intent. Confirm is offered only for an offer the server marked purchasable, and for a store product only while no store payment of another offer is still unfinished. While the purchase is in flight, store payment included, the preview cannot be closed or switched to another offer and a second confirm sends nothing; the answer moves it to `Done` with a `ShopCheckoutResult` (`InStore`, the `ShopBuyResult` or the `ShopPurchaseResult`, `Granted` and one `MessageKey`), so a failed purchase, `shop.buy.insufficient` and `shop.purchase.store_unavailable` show in the same preview. After an in-game answer that does not settle the intent (`ShopBuyer.IsUnsettled`: no response, rate limit, a server error or an unreadable success) confirm stays available and retries with the same request id; after a store payment the server has not settled (`ShopPurchase.CanRetry`) confirm sends the same receipt again, also from a preview of that offer opened later; after a purchase, a refusal or a store answer before payment it does not, and a fresh preview starts a new purchase. The client checks no balance or price itself. `NetBoot.Checkout` builds it with `new ShopPurchase(NetBoot.Api, new NoStoreBilling(), NetBoot.Integrity.Request)`, so until a billing SDK is on the client (#851) a store product ends at `shop.purchase.store_unavailable` without a request. The `ShopCheckoutTests` EditMode tests cover the two taps, the routing of in-game and store offers (premium pass included), the refused, unavailable and in-flight cases, insufficient balance and the retries of both paths.

`Game/Shop/ShopPurchase` is the store product purchase flow of `docs/economy.md` 7.5 (#105) behind a billing seam, `IStoreBilling`; no billing SDK is on the client yet, so `NoStoreBilling` answers every purchase as unavailable; `ShopCheckout` sends every store product through it. `Buy` takes an offer id and runs one purchase at a time: without store billing it answers `StoreUnavailable` (`shop.purchase.store_unavailable`) and sends nothing; otherwise it posts `{"offer"}` to `POST /shop/begin`, hands the server's `product_id` and `account_token` to `IStoreBilling.Purchase`, and, once the store returns a receipt (`StoreReceipt`: platform `google` or `apple` and the purchase token or signed transaction), asks for a `purchase` integrity proof (`docs/anti-cheat.md` 5.1, the `Action<IntegrityPurpose, Action<IntegrityProof>>` that `NetBoot.Integrity.Request` fits) and posts `{"offer","platform","token"}` to `POST /shop/complete` with the proof as `X-HD-Play-Integrity` or `X-HD-Attest-Key`, `X-HD-Attest-Nonce` and `X-HD-Attest-Assertion` (`Net/Integrity/IntegrityHeaders`); no proof sends no header and the server's policy decides. `ShopPurchaseResult` carries one `ShopPurchaseOutcome`, the step it ended at and the `ShopCompleteReply` as sent (`state`, `crystals`, `finished`, `repeated`). A refusal of `/shop/begin` comes before any payment and shows the same `shop.buy.<reason>` key as a coin purchase (`offer.in_game_only`, 503 `purchases.disabled`, `purchase.blocked` and the rest); a store cancel shows nothing, a deferred payment `shop.purchase.pending`. After the store took the payment, every refusal of `/shop/complete` (`receipt.*`, `integrity_failed`, `bad_integrity_proof`, `purchase.platform_unavailable`, `pass.no_season`, an offer code or one a newer server adds) keeps its reason as the outcome but shows `shop.purchase.not_granted`, since the store refunds a purchase the server never granted, and the receipt is dropped. No response, the limiter, a lost session, a 5xx (`integrity_unavailable`, `receipt.store_unavailable`) or an unreadable success keep the receipt in memory: `CanRetry` is true, `Buy` refuses another offer, and `Retry` asks for a fresh proof and sends the same receipt again, which the server answers idempotently on the transaction id; a 5xx or an unreadable success shows `shop.purchase.unfinished`. A `granted` answer is `shop.buy.bought`; a `pending` one is `shop.purchase.pending` and the store transaction is left open; any answer the server recorded and that is not pending calls `IStoreBilling.Finish` with the receipt and the server's `finished`, so the store transaction is finished only after the grant (`docs/economy.md` 7.5 step 5). Nothing is stored on the device. The `ShopPurchaseTests` EditMode tests cover the three requests, the receipt body and proof headers, every refusal of both steps, the store outcomes, the retry with a fresh proof and the shipped texts of every key.

`Game/Shop/ShopLoader` fetches what the shop screen shows (#105). `Load` sends `GET /shop` and, once the showcase reads, `GET /wallet` (`ShopLoader.WalletPath`) through `ApiClient`, and answers one `ShopLoadResult`: `Loaded` with the `ShopShowcase` and the `Balances` as sent (a negative balance after a refund stays as is), or the first failure. A second load while one is in flight sends nothing, so the view can reload after a purchase or on return without doubling requests. No response is `shop.load.offline`, the limiter's `rate_limited` is `shop.load.rate_limited`, a lost session has no key and goes back to sign-in, and every other reply, including an unreadable showcase or wallet, is `notice.generic`. The built-in bundle holds the `en` and `az` text of every key. Nothing is cached on the device. The `ShopLoaderTests` EditMode tests cover the two requests, the single load in flight and each failure of either reply.

`UI/Localization/Resources/builtin-strings.json` is the built-in bundle (`docs/localization.md` 2.2) for keys the client needs before a published bundle arrives, starting with the currency names of `docs/economy.md` OQ-13. `BuiltinStrings.Load` reads it from `Resources`; `BuiltinStrings` gives the built-in value of a key in one language. The `ShopTests` EditMode tests cover these types.

## Promo codes

`Game/Promo` is the model of the promo code entry (#109, `docs/economy.md` 8); the server decides whether a code is valid and what it grants. `PromoCode.TryNormalize` applies the server's own format check (`server/internal/promo` `Normalize`): spaces, `-` and `_` are dropped, letters are upper-cased without culture, every other character must be in the alphabet without look-alikes, and 4 to 32 characters must remain. A code that fails it is answered with `promo.redeem.code_invalid` without a request; the server refuses such a code the same way, before it counts an attempt. `PromoRedeemer.Redeem` posts the normalised code to `POST /promo/redeem` as `{"code"}` through `ApiClient`, so it is signed with the request MAC, and refuses a second submit while one is in flight, since every request counts toward `PromoAttemptsPerHour`. `PromoRedeemResult.From` turns the reply into one `PromoRedeemOutcome`: a grant keeps the coins, granted cosmetics, pass XP and dropped pass XP the server reported, `PassPremium`, true only when the reply's `pass_premium` says this redemption unlocked the premium Hype Pass track, and `Duplicates`, the cosmetics already owned with the coins paid for each as duplicate compensation (`docs/economy.md` 2.7); each `promo.*` refusal has its own key `promo.redeem.<reason>`; `promo.rate_limited` and the limiter's `rate_limited` are `promo.redeem.rate_limited`, `promo.locked` is `promo.redeem.locked`, no response is `promo.redeem.offline`; every other reply, including a reason a newer server adds, is `notice.generic` (`docs/localization.md` 3). A lost session has no message key and goes back to sign-in. Every other outcome has its own key, and the built-in bundle holds its `az` and `en` text, `notice.generic` included (`docs/economy.md` 8, Reply texts). `PromoCodeEntry` is the state of the input field: `Edit` takes the field text on every change and runs `PromoCode.IsWellFormed`, the same check without allocating, so `CanSubmit` is true only for a well-formed code with no request in flight; `Paste` replaces the text with the clipboard text the screen reads on the paste tap, unchanged, and an empty clipboard keeps what was typed; `Submit` sends the text through `PromoRedeemer`; `MessageKey` holds the key of the last reply until the next edit, and `Redeemed` passes the full result on for the reward view and the sign-in return. A grant whose reply unlocked the premium Hype Pass track (`PassPremium`) has the key `promo.redeem.granted_pass_premium` instead of `promo.redeem.granted`. `PromoCodeView` is the screen: `Bind(entry, strings)` passes every field change to `Edit`, the paste button reads `GUIUtility.systemCopyBuffer` into `Paste`, the redeem button calls `Submit` and is interactable only while `CanSubmit`; while `Busy` the field is read-only and paste is off; the message line shows the game string of `MessageKey` and hides without one, and follows a language change. The view decides nothing; its prefab, art and the entry points in settings and the shop are #848. `Game/GrantDuplicates` reads `grant.duplicates` of a promo or shop reply, a JSON map that `JsonUtility` cannot read, with `Net/JsonMap`: a missing or `null` grant or map is none; a grant or map that is not an object, or an amount that is not a whole number of at least 0, makes the reply a failure (`notice.generic`). The `PromoCodeViewTests` PlayMode tests cover the view. The `PromoRedeemTests` EditMode tests cover the format check, its zero allocation, every reply, the distinct keys and their shipped texts, the single request in flight and the entry.

## Friend lobby

`Game/FriendLobby` is the model of the friend lobby and team setup (#154, `docs/friend-lobby.md` FL-1, FL-2); the server decides membership, leadership, mode, seats and the start. `RoomCode.TryNormalize` keeps a typed room code only when it can match a code the server creates (`server/internal/custom`): spaces are dropped, letters are upper-cased without culture, every character must be in the server's alphabet without `0`, `1`, `I` and `O`, and exactly 6 must remain. The server looks a code up as sent, so any other input is not sent. `FriendRoom.Read(state, localAccount)` reads each `LobbyState` the session raises: code, leader, members in join order, phase, mode and refusal, the seats of the mode split into the two team columns by `SeatOrder.TeamOf` (N and S or X against E and W or Y, R-6, R-8), the local seat, and the members without a seat, who wait in the lobby. An empty state means the player is in no room. What the screen offers follows the server's checks: `CanStart` only for the leader in team setup with every seat filled, `CanGoBack` for the leader in team setup, `CanChooseMode` for the leader outside a match, `CanInvite` for any member outside a match while fewer than 4 members are in, and `CanRequestSeat` for a member other than the leader, in team setup, for another seat of the mode. `LobbyCommands` sends one reused `LobbyIntent` per command (`CREATE`, `JOIN`, `LEAVE`, `TEAMS`, `BACK`, `PLACE`, `REMOVE`, `START`, `INVITE`, `REQUEST_SEAT`, `ADD`) on an accepted session only, carrying just the fields of that command; `TryJoin` sends the normalised code and refuses a code that fails the check. `RoomInvites.Follow(session)` keeps the in-game invites (`LobbyInvite`) a friend sent while they wait for an answer, one per room with its latest inviter, in arrival order; an invite whose code fails the check, without an inviter, or to the room the player is in is dropped. It reads each `LobbyState` for the player's room: entering a room drops its invite, and `CanAccept` holds only outside a room, mirroring the server's `ALREADY_IN_LOBBY`. `TryAccept` sends `JOIN` with the invited code through `LobbyCommands` and drops the invite once sent; `Decline` drops it. The server still decides the join (R-58, a full or started room). `AppFlow.Room` follows each `LobbyState` from the session (`AppBoot.Listen`) for the app state `Room` (FL-1 and FL-2): entering a room from the lobby opens it and leaving it returns to the lobby; a custom match starts from the room on its first match view; when the match ends, a member still in the room returns to it as soon as the server puts the room back outside the match phase (FL-5), and leaving a finished match goes to the room while the player is in one, else to the lobby. A room seen before an accepted hello is forgotten, because a disconnect outside a match leaves the room. `FriendRoom.RefusalKey` names the game string of the state's `LobbyRefusal` through `LobbyRefusalKeys.Of`: `lobby.room.refused.<reason>` for every reason the server sends, `notice.generic` for any other, and none when nothing was refused; a typed code that `TryJoin` refuses shows `LobbyRefusalKeys.UnknownCode`. A `CREATE` or `JOIN` during a ranked ban is refused `lobby.room.refused.ranked_ban` (owner decision 1 of #186); `RefusedUntilUnixMs` and `BanReason` carry its end and category, `BanReasonKey` names `ban.reason.<category>` like the queue, and `SecondsUntilBanEnds` counts to the end from `ServerClock`, 0 without an end or a synced clock; `Appeal` is the appeal grant of the state (Appeals), replaced by every state read. The built-in bundle holds their `az` and `en` texts (`docs/friend-lobby.md` 4, Refusal texts). The setup screen, the result shown in the room, the invite prompt view and the invite link are not built yet: no link format is defined. `AppFlowTests` cover the room states. The `FriendLobbyTests` EditMode tests cover the code check, both team layouts, leader and member offers, the lobby and match phases, leaving the room, every command's fields, the invites, the refusal and ranked ban keys, their shipped texts and that naming one allocates nothing.

`RoomMembers.Read(room)` turns each read `FriendRoom` into the members panel of FL-1 (#279): one `RoomMember` per member in join order with the account, `IsLeader`, `IsLocal` and the seat (`Seat.Unspecified` while waiting in the lobby). `LobbyState` carries account ids only, so the look comes from each member's public profile (`GET /profile/{account}`, `proto/README.md`): `RoomMembers` asks for one profile at a time through its own `ProfileLoader`, and `Profile`, `Nickname`, `AvatarId` and `FrameId` stay empty until it arrives. A profile is kept while its member stays in the room and is not asked for again on later states; a failed load moves on to the next member and is asked again on the next state; a profile that arrives after its member left is dropped, and leaving the room forgets every profile, so a room entered again shows the current look. `Changed` fires on every read and every arrived profile. There is no ready state in the room: the server has none, readiness belongs to the loading screen (FL-3). `LobbyEmoji` is the lobby emoji (#150, #151, `docs/friend-lobby.md` 2). It keeps the own emoji loadout from the `GET /inventory` reply (with its `emoji_slots`) and each `PUT /inventory/equip` reply like `MatchEmoji`, and puts it on its `EmojiWheel` when the player enters a room, because the server keeps the emoji a member joined with; leaving the room empties the wheel. `TrySend` sends the tapped slot as one reused `EmojiIntent` on an accepted session, only while the room is in the lobby phase, the one phase where the server takes a lobby emoji. Each `LobbyRelay` with an `item_id` from a member of the room raises `Shown` with the account and the emoji for the view to show over that member's avatar; the own emoji coming back calms the wheel as in a match, and a seat request or a relay from outside the room shows nothing. `FriendLobbyLink` wires both into the running app (`FriendLobbyBoot.Link`, built by `NetBoot` right after `NetBoot.Room` starts reading, so the room has read each state first). `Follow(session)` reads every `LobbyState` into `Members` and, on each accepted hello, loads `GET /inventory` through its own `InventoryLoader` and passes the reply to `Wear`. Its `Invites` is the `InvitePanel` below on `NetBoot.Lobby`: each read `LobbyState` calls `RoomChanged`, entering a room loads the friends list once, `TryInvite(friend)` sends on the followed session and refuses without one, and `FriendsLoaded` passes on the load outcome; one other than `Loaded` is logged as `Friend lobby friends outcome=<outcome>` and asked again on the next room entry. The `EmojiWheel` and its `LobbyEmoji` exist from the first inventory reply on, with the reply's `emoji_slots` as the wheel's capacity, since the slot count is server config (`HD_EMOJI_SLOTS`); a later reply with more slots builds a larger wheel and only the new one follows the session, fewer slots keep the wheel. An inventory that arrives inside a room fills the wheel at once; `Wear(EquipReply)` reaches the wheel in the next room, as above. `TrySend(slot)` sends on the followed session with the boot's clock (`Time.realtimeSinceStartupAsDouble` in ms), and `EmojiShown` passes on each `LobbyEmoji.Shown`. A load other than `Loaded` is logged as `Friend lobby inventory outcome=<outcome>` and retried on the next accepted hello; a retry policy is not decided. No screen reads them yet: the members panel, its art and the emoji over the avatar are #848. `RoomMembersTests`, `LobbyEmojiTests` and `FriendLobbyLinkTests` cover them.

`InvitePanel` is the invite panel of FL-1 and FL-2 (#279, `docs/friend-lobby.md` 2, Invite). `Game/Friends` reads the friends list: `FriendListLoader.Load` asks `GET /friends` (`docs/friends.md` 4) one load at a time and keeps only `friends`, each as a `Friend` with the account, nickname and `FriendPresence`; `incoming`, `outgoing` and `blocked` are not kept, and a presence other than `online` or `in_match` reads as `Offline` (FR-15). A reply that cannot be read, or a friend without an account id, fails the load with `Failed` and keeps the list from before; a refused request names `Offline`, `SignInRequired`, `RateLimited` or `Failed` like `LobbyHeaderLoader`. `InvitePanel.Load` loads the list into the panel and raises `Changed`; `Friends` and the room `Code` are what the panel shows. `StateOf(friend)` names each row without allocating: `AlreadyInRoom` for a member of the room, `RoomClosed` while `FriendRoom.CanInvite` does not hold (no room, a full room or a running match), `Offline` for an offline friend, who gets the room code to type, `InMatch` for a friend in a match, `Invited` once an invite went out, and `Invitable` for an online friend otherwise. `TryInvite(session, friend)` sends `INVITE` through `LobbyCommands` only for an `Invitable` friend and marks them `Invited`, so a second tap sends nothing; the server answers a sent invite only with a refusal or a later room state, so `RoomChanged`, called on each read `LobbyState`, clears every mark and the friend can be invited again. The server still decides (friends only, blocks, `IN_MATCH`, a full room). ## Missions

`UI/Missions` turns the server's mission board into what the missions screen shows, without computing progress or rewards (`docs/pass-missions-medals.md` section 4, PM-1 to PM-3). `MissionBoardReply` reads `GET /missions` and the board `POST /missions/reroll` answers with, using `JsonUtility`. `MissionBoard.TryFrom` sorts the assignments into the `Daily`, `Weekly` and `Achievement` tabs in the order the server sent; any other mission type is left out until its tab exists. A `MissionCard` holds the id, the name key (`mission.<slug>.name`, formatted with `{target}`), the target, the progress as sent and whether `completed_at` is set; `ShownProgress` and `Fill` keep the bar inside the target and full once completed. There is no claim: the server grants a completed mission at once (PM-3), so a card has no claim state. `CanReroll` is true for an uncompleted daily or weekly card while the board's `daily_rerolls` or `weekly_rerolls` is above 0; the server still decides, and its refusal code (`mission.reroll_used`, `mission.not_assigned`, `mission.no_replacement`) comes back in `ApiReply.Error`. `RerollRequest.Json` is the intent body `{"mission"}`. `DailyResetUnixMs` and `WeeklyResetUnixMs` are the ends of the board's `day` and ISO `week` at 00:00 UTC (`docs/economy.md` section 2), and `TrySecondsUntilReset` counts a daily or weekly tab down to its reset with `ServerClock.TrySecondsLeft`, never reading the device clock; it runs only once the clock is synced and never for the `Achievement` tab, which has no reset. `IsPastReset` turns true when the board's economy day has ended on server time, the earliest of the two resets, so the screen fetches `GET /missions` again instead of showing a past period; a board that does not carry a readable `day` and `week` is refused. Reading a board allocates nothing. The `MissionBoardTests` EditMode tests cover the tabs, progress, completion, reroll offer, intent body, reset times across month and year ends, the reset countdowns and the past-reset check on server time, refused periods and 0 B reads and ticks.

`Game/Missions/MissionLoader.Load` sends `GET /missions` through `ApiClient` (refresh on `access_expired`) and answers one `MissionLoadResult`: `Loaded` with the `MissionBoard` of that body, or the failure. A second `Load` while one is in flight sends nothing. No response is `mission.load.offline`, `429` is `mission.load.rate_limited`, a lost session has no key and goes back to sign-in, and every other reply, including the server's `503 mission.unavailable` and a body that `MissionBoard.TryFrom` refuses, is `notice.generic`. Both keys ship in the built-in bundle with `en` and `az` texts. `MissionLoaderTests` cover the request, the single load in flight, every failure and the built-in texts.

`Game/Missions/MissionReroller.Reroll(board, card, done)` sends the reroll intent `POST /missions/reroll` with `RerollRequest.Json(card.Id)` only when the board offers it (`MissionBoard.CanReroll`: an uncompleted daily or weekly card with a reroll left), so a completed card, an achievement or a spent period sends nothing; a second reroll while one is in flight sends nothing either. It answers one `MissionRerollResult`: `Rerolled` with the `MissionBoard` the server answered with, which replaces the shown board as is (the new mission, its progress and the rerolls left all come from the server), or the failure. The server's `409` codes are `mission.reroll.used` (`mission.reroll_used`), `mission.reroll.not_assigned` (`mission.not_assigned`, the shown board is out of date) and `mission.reroll.no_replacement` (`mission.no_replacement`); no response is `mission.reroll.offline`, `429` is `mission.reroll.rate_limited`, a lost session has no key and goes back to sign-in, and every other reply, including `503 mission.unavailable` and a body `MissionBoard.TryFrom` refuses, is `notice.generic`. These five keys ship in the built-in bundle with `en` and `az` texts. `MissionRerollerTests` cover the intent, the single reroll in flight, the cards that send nothing, every refusal and the built-in texts.

`Game/Missions/MissionListView.Bind(loader, strings)` loads the board and shows one tab (`ShowTab`, `Daily` first) in a `UI/Lists/RecyclingList` built from a `MissionRowSlot` template (row height from the template, `TokenSpacing.Sm` between rows): each card in the server's order with its name (`NameKey` formatted with `{target}`), the shown progress and the target as numbers, the bar filled to `Fill`, and the completed mark when the server set `completed_at`. Names and numbers are formatted once per load, per tab and per language change, so binding a row while scrolling formats nothing. A refused load shows no rows and no message, like the other list views. The reward, the reroll button, the reset countdown and the mission-complete effect are not built yet. `MissionListViewTests` (PlayMode) cover the tabs, progress, completion, number format and a failed load.

## Sign-in

`Net/Auth/AuthSession` is the client side of `POST /auth/nonce`, `/auth/signin`, `/auth/refresh` and `/auth/logout` (`server/internal/auth`). It is plain C# behind three seams:
- `IIdentityProvider` is the native Google or Apple sign-in. It gets the nonce to put in the ID token: the server nonce for Google, its lowercase SHA-256 hex for Apple. It answers a token, `Cancelled` or `Failed`.
- `IAuthTransport` posts JSON and answers the status and body; status 0 means no response.
- `ISecureStore` is the platform secure storage (Keystore, Keychain; `docs/privacy.md` P-1). It holds only the refresh token (`auth.refreshToken`) and a random device id made once (`auth.deviceId`), never a hardware identifier.

`SignIn` gets a nonce, asks the provider for an ID token and sends it with the raw nonce and the device id. `Resume` is the silent sign-in at later starts: it refreshes the stored token with the same device id. The access token, the request key and the account id stay in memory only.

Outcomes:
- `SignedIn`, with `NewAccount` set on the first sign-in so the profile setup can follow.
- `Cancelled` when the player closes the account picker, `ProviderFailed` when the SDK fails.
- `Offline`, `Unavailable` (5xx or an unreadable reply) and `RateLimited` (429). A refresh that fails this way keeps the stored token.
- `Rejected` for a refused sign-in, `Banned` with `BanCategory`, the reason category of the server reply (`{"error":"banned","category"}`, `docs/admin.md` 6.2; empty when the reply has none), `BannedUntilUnixMs`, the end of the reply's `banned_until` (RFC 3339 UTC; 0 for a permanent ban, which carries none, and for a value that does not parse) and `Appeal`, the appeal grant of the reply's `appeal` (Appeals below), `Deleted` and `DeletionPending` with `DeleteAt`. A refresh refused this way forgets the stored token; a refused refresh token answers `SignInRequired`.
- `Busy` while another call runs, `Unsupported` when the platform has no such provider.

`SignOut` forgets the session at once and revokes the refresh token on the server. The `AuthSessionTests` EditMode tests cover these flows.

`Net/Auth/SignInOptions` is the list of sign-in buttons the login screen shows, in order: Google on Android; Google, then Sign in with Apple next to it on iOS (`docs/store-listing.md` DC-5); none on platforms without a native sign-in, such as the editor and desktop. `Current` reads `Application.platform`. The `SignInOptionsTests` EditMode tests cover each platform. The native Google Sign-In and Sign in with Apple plugins and the Keystore and Keychain store are not built yet. Until they are, `NetBoot` uses two stand-ins:
- `Net/Auth/NoIdentityProvider` supports no provider, so `SignIn` answers `Unsupported` (#56 replaces it).
- `Net/Auth/MemorySecureStore` keeps the refresh token and device id in memory only and writes nothing to the device. Every start therefore begins without a stored session and shows `Login`.

`Game/Login/LoginScreen` is the model of the `Login` state (#73), plain C# without a view. `Options` are the buttons of `SignInOptions.Current`. `TrySignIn(provider)` starts `AuthSession.SignIn` for an offered provider and refuses a second tap while `Busy`; a signed-in answer calls the start action, which `NetBoot` sets to its dial, so the hello then moves the flow on (a new account meets the profile setup in the lobby). Every other answer sets `MessageKey`, and `Changed` tells the view to redraw:
- Closing the account picker shows nothing, and the player can tap again.
- `login.unsupported` (no native provider on the device), `login.unavailable` (5xx or an unreadable reply), `login.rejected` (a refused ID token) and `login.banned` are new keys, `en` and `az` drafts in the built-in bundle. A ban also sets `BanReasonKey` to `ban.reason.<category>` through `BanReasonKeys.Of(category)` (`cheating`, `collusion`, `afk_leaving`, `offensive_name`, `payment_fraud`, `other`; owner decision 2 of #186), shown under `login.banned`, which stays the headline because the reason texts read "Reason: ...". An unknown or missing category shows `ban.reason.other`, the category the server itself gives a ban without one, so a ban always names a reason and a newer server category never shows an empty line. Detection details are never sent. Any other answer and every new tap clear `BanReasonKey`. A temporary ban also sets `BannedUntilUnixMs` from the reply's `banned_until`; `SecondsUntilBanEnds(clock, now)` counts to it from `ServerClock` like the queue and room bans, never the device clock, and is 0 for a permanent ban (no end), without a synced clock or once the end has passed. The view shows it under `login.banned` as `login.banned.ends_in` with the `{time}` argument (`LoginKeys.BanEndsInArgument`), a new key with `en` and `az` drafts; a permanent ban shows no end. `BannedUntilUnixMs` is cleared like `BanReasonKey`. A ban with an appeal grant also sets `Appeal` (Appeals below), cleared the same way. The provider failure, offline, rate limit and deleted answers reuse the `account.deletion.*` texts, which say the same.
- An account waiting for deletion sets `DeletionPending` and `DeleteAt` with the pending text of `AccountDeletionKeys`; `TryCancelDeletion` sends `AccountDeletion.Cancel` with the provider just used, and a restored account shows `account.deletion.restored` and signs in on the next tap (`docs/privacy.md` 8.2, Grace).

The `LoginScreenTests` EditMode tests cover these rules and that every message key is in the built-in bundle in `az` and `en`. The view of the screen is art work.

Appeals (#186, owner decisions 4 and 5, `docs/admin.md` 6.4, Appeals) are plain C# without a view. `Net/SanctionAppeal` is the appeal grant a server answer carries: `SanctionId`, `Token` and `ExpiresUnixMs`; `Offered` holds only with a positive sanction id and a token, so an answer without a grant (a ban recorded before sanction rows) offers no appeal. `SanctionAppeal.Of` reads the JSON `{"sanction_id","token","expires_at"}` and `SanctionAppeal.FromWire` the wire `AppealGrant`. Each model keeps the grant of the latest answer: `AuthResult.Appeal` and `LoginScreen.Appeal` from the sign-in `banned` refusal, `MatchQueue.Appeal` from a `RANKED_BAN` or `MATCHMAKING_BAN` `QueueState`, `FriendRoom.Appeal` from a `RANKED_BAN` `LobbyState`, and `PlayerProfile.RenameAppeal` from the `rename_appeal` of `GET /profile/me` while `RenameRequired`. The token lives in memory only, never in device storage, and a new answer replaces it; the client never checks its expiry, the server refuses an expired one. `Game/Lobby/AppealSender.Send(appeal, text, done)` posts `{"sanction_id","text"}` to `POST /appeals` through the `IApiTransport` with `Authorization: Bearer <appeal token>` and no request MAC, one appeal at a time and only with an offered grant. The text goes as typed: the server trims it and judges its length against `AppealTextMaxLength`, which the client does not know. `AppealResult` carries the `ApiOutcome`, the status and the server's `error`, and `MessageKey` names its text through `AppealKeys`: `appeal.sent` on 201; `appeal.refused.expired` for `appeal_token_expired`, `appeal_token_rejected` and `sanction_mismatch` (the next answer brings a new grant); `appeal.refused.text_required`, `appeal.refused.text_too_long`, `appeal.refused.open`, `appeal.refused.rejected` (a rejected appeal is never sent again), `appeal.refused.ended` and `appeal.refused.not_appealable` (a shadowban goes through support) for the refusals of the same name; `appeal.offline` without a reply; `appeal.unavailable` for 429 and 5xx; `notice.generic` for `malformed`, `unknown_sanction` and any other refusal. The built-in bundle holds `en` and `az` drafts of every key. The `AppealTests` EditMode tests cover the request, every refusal and outcome, reading both grant forms and the shipped texts; `AuthSessionTests`, `LoginScreenTests`, `MatchQueueTests`, `FriendLobbyTests` and `PlayerProfileTests` cover where each grant arrives. The appeal form view is art work (#848).

With no identity provider and no server dev identity path, a build reaches `Login` but cannot sign in or connect end to end yet.

`Net/Api/ApiClient` sends every other player HTTP request (leaderboard, profile, push settings, shop and the rest) with the session of `AuthSession`:
- Each request carries `Authorization: Bearer <access token>`. Each POST, PUT, PATCH or DELETE also carries `X-HD-Mac`, the request MAC of `docs/anti-cheat.md` V-4 (`Net/Api/RequestMac`), so every write is signed whether or not its route checks it yet.
- A 401 `access_expired` refreshes the session once through `Resume` and sends the request again with the new token and MAC. Requests made or expiring while the refresh runs wait for it and share it; a second expiry after the refresh, or a failed refresh, answers them all.
- `Post` can take extra headers (`ApiHeader`, for the integrity proof of `POST /shop/complete`). They are sent through `IApiHeaderTransport`, which `UnityHttpTransport` implements, and again with a refreshed request; they are not part of the MAC. A transport without it sends the request without them.
- Outcomes: `Ok` (2xx), `Offline` (no response), `SignInRequired` (no session, `access_rejected`, a second `access_expired`, or a refresh that ended the session), `RateLimited` (429), `Unavailable` (5xx), `Rejected` (any other refusal). The server's error code is kept in `Error` and the body in `Body`.

`Net/JsonMap` reads the JSON objects of a reply that `JsonUtility` cannot, because their keys are data (level numbers, modes, item ids). It parses with the `JsonParser` of `Google.Protobuf` into a `Struct`, so no parser of our own is kept and malformed JSON is refused. `Keys` lists the members; `TryMap`, `TryString`, `TryInteger` (a whole number up to 2^53), `TryStrings` (a list of strings only) and `TryMaps` (a list of objects only) read a member of that kind and nothing else; `IsAbsent` is true for a missing member or `null`. Parsing allocates, so it is for replies, never a frame. The `JsonMapTests` EditMode tests cover it.

`Net/Api/UnityHttpTransport` is the `UnityWebRequest` transport for both `ApiClient` and `AuthSession`; the base URL and the timeout are passed in by whoever builds it. The `ApiClientTests` EditMode tests cover the flows, and two MAC vectors were checked against the server's `token.SignRequest`.

## Effect pools

`UI/Motion/EffectPool` and `UI/Motion/ParticleBudget` hold the effect instances and particles of `docs/ui-motion.md` 7, Budgets per effect.

- **`ParticleBudget`:** create one per scene with the effect level and reduce motion, and call `Configure` when either changes. `Take(kind, wanted)` grants at most the effect's particles at the level and at most what is left of the level's `MaxParticles`. With reduce motion both caps use the low level. `Return(count)` gives particles back.
- **`EffectPool`:** create one per effect when the match scene loads. It has `TokenEffect.PooledOfKind` slots and nothing is created later.
  - `Begin(nowMs, wantedParticles)` takes a free slot. When every slot is live, it ends the oldest one and reuses it. It returns the slot and grants its particles from the shared budget.
  - `Tick(nowMs)` ends instances that reached the effect's `DurationMsOfKind`. It runs inside the `Effect.<name>` profiler marker (`MarkerNameOf(kind)`, also `Marker`), so a component that draws the effect does its per-frame work in that marker.
  - `End(slot)` ends one instance early and `EndAll` is the jump to the final state of `docs/ui-motion.md` 6 rule 5. Both give the particles back.

The `EffectPoolTests` EditMode tests check every effect's particles and pool size against the budget table, the level caps, reduce motion, eviction, expiry, the `turn` set and 0 B per frame. `UI/Effects/EffectPlayer` draws the particles (below).

`UI/Effects` holds the shared effect sprites, their one atlas, the additive and alpha effect materials and `effects.json`, the definition of every effect per level (`docs/vfx.md`). `Editor/EffectsContent.ImportAllAndExit` (menu HypeDomino > Import Effects, or the `Unity editor method` workflow) sets the sprite import, the atlas and the materials; `EffectsContentTests` check them and `node tools/vfx/vfx.mjs` checks `effects.json` against the budgets.

## Effect player

`UI/Effects/EffectPlayer` draws every effect of `effects.json` as pooled quads (`docs/vfx.md` section 7).

- **Build once.** `Build(library, sprites, additive, alpha, level, reduceMotion)` (or `Awake` with the serialized `effects.json`, sprites and the two shared materials) parses nothing per frame: `EffectLibrary.Parse` reads `effects.json` once and refuses an unknown sprite, a tint that is not a colour token or `team`, a glow that is not a glow token or `step`, a count over the effect's particle budget, overdraw over the level's `maxOverdrawLayers` and an effect without a budget. Build makes the player a sub-canvas with two `EffectQuads` graphics, one per shared material, each with room for the high level's `maxParticles` plus every pooled instance's sprites, and one `EffectPool` per effect over one `ParticleBudget`. Nothing is created after it.
- **Play.** `Play(EffectRequest)` begins an instance in the effect's pool, takes its single sprites from the effect level and its particles from the budget's particle level (low with reduce motion), and splits the granted count over the particle entries in their proportions (the score steps of `docs/vfx.md` section 5). `EffectRequest.On(kind, area or point, startMs)` sets where and when; `ForTeam` gives the `team` tint, `AtStep` the score step and its glow, `TrailFrom` a trail that arrives (the bursts follow its end) and `TrailTo` one that leaves.
- **Tick.** `Tick(nowMs)`, called from `Update` with unscaled time, ends instances at their max ms, drops their quads and moves the rest inside the `Effect.player` marker (`EffectPlayer.ProfilerMarkerName`); each pool's own `Effect.<name>` marker wraps its expiry. Single sprites pop in and out like the score popup (`UI/Motion/ScorePopup`), so with reduce motion they fade without the scale pop; particles burst out over the request's area with `enter` and fade with `exit`; trails travel with `standard`. `Configure(level, reduceMotion)` ends everything playing when either changes.
- **Hooks.** `TilePlaceLayer.Attach(player)` plays `tilePlace` for each placement that is not jumped, with the trail from the hand and the dust when the tile settles; `TilePlaceLayer.LastPlaced` is the tile placed last. `SeatEmojiLayer.Attach(player)` plays `emoji` at the seat. `Game/Match/MatchEffects.Read(view, nowMs)` reads each `MatchSnapshot` through `EffectCues` and plays the score cascade per team (at the last tile with its trail to the meter, or at the meter for hand points), `domino`, `block` and `matchWin`, timed by `docs/ui-motion.md` 7, Concurrency.

`EffectLibraryTests` and `EffectPlayerTests` (EditMode) cover parsing the committed file and refusing broken ones, level selection, the score step split, the per-effect and per-level particle caps, pool eviction, expiry, reduce motion, glows, team tints, trails and the two materials; `EffectCuesTests` (EditMode) cover the view reading. `EffectPlayerFrameTests` (PlayMode) play a scripted match for 600 frames at every level and with reduce motion, including the canvas rebuild, and assert 0 B GC in every frame, the live particle cap in every frame and the update marker.

## Content

`Content` holds the client side of `docs/content-delivery.md` on Addressables 2.10.3, the version Unity 6000.3 ships. `CatalogUpdater` decides when a remote catalog is downloaded, committed, retried (2 s, 8 s, 30 s) or held back until a match ends; it is plain C# behind `ICatalogSource` and covered by the `CatalogUpdaterTests` EditMode tests. `AddressablesCatalogSource` downloads the catalog to `persistentDataPath/content`, keeps it there as `catalog_<version>.bin`, loads it with `Addressables.LoadContentCatalogAsync`, keeps only the last remote locator and stores its version and root in `PlayerPrefs` (`content.catalogVersion`, `content.baseUrl`). Every successful load runs `Addressables.CleanBundleCache`, which reads the loaded catalogs from their files and removes cached bundles none of them references (CD-24). ## Settings screen

`Game/SettingsModel` is what the settings screen (#157) binds to. It takes the stores the boots already keep, `LanguageBoot.Choice`, `AudioBoot.Volumes`, `MotionBoot.Motion`, `GraphicsBoot.Quality`, `GraphicsBoot.FrameRate`, `Haptics.Preference` and `ContentBoot.Cache`, and exposes them as the rows. A row changes its store directly, so it applies at once and is saved as each store already does (the audio levels when the app pauses). `Changed` is raised once for every value that really changes in any row, including a graphics level (forwarded by the frame rate policy, so it counts once), a system reduce motion change while the row follows the system, and a cache clear that cleared at once, so the screen formats its texts only then. `ClearCache` returns the `CacheClearResult` for the screen to show, and `Game/CacheClearKeys.Of` names its game string key (`docs/content-delivery.md` 7), whose `en` and `az` texts ship in the built-in bundle, covered by `CacheClearKeysTests`. `Dispose` stops listening when the screen closes. `SettingsModelTests` cover it. The screen itself, its texts and its layout are not built yet.

`Game/Push/PushSettings` is the model of the push notification rows (#157, `docs/push.md` 3). The server keeps the settings; nothing is stored on the device. It is built with the `PrivacyPolicyVersion` the player saw and the app version, and refuses to be built without either, because a change of the promotional category is recorded as consent with both (PN-9). `Load` reads `GET /push/settings`; `SetGameplay` and `SetPromotional` send `PUT /push/settings` `{gameplay, promotional, policyVersion, appVersion}` through `ApiClient`, so they are signed with the request MAC, only after a load and never while another request is in flight. `Gameplay` and `Promotional` change only to what the server answered, and `Changed` is raised only when a value really changes. `PushSettingsResult.From` turns a reply into one `PushSettingsOutcome`: no response is `push.settings.offline`, the limiter's `rate_limited` is `push.settings.rate_limited`, a success has no message key, a lost session has no message key and goes back to sign-in, and every other reply, including `push.malformed`, `push.consent_context_required` and an unreadable success, is `notice.generic`; a failure keeps the last values the server sent. The keys ship in the built-in bundle with `en` and `az` texts. The Settings screen rows are not built yet. `PushSettingsTests` cover it.

`Game/Push/PushDevice` registers the FCM or APNs token of this device (#157, `docs/push.md` PN-4, PN-5, PN-10). It is built with the platform, `android` or `ios`, and refuses any other. `Register` sends `PUT /push/devices` `{token, platform}` through `ApiClient` unless the token is the one the server already accepted; one request is in flight at a time and a token rotated meanwhile is sent after it. A failure is not retried on its own; the next `Register` (sign-in or a rotation) sends it again. `Unregister` forgets the token, sends `DELETE /push/devices` `{token}` and calls back whatever the server answers, so logout waits for it but is never blocked by it. The token is never stored on the device. `PushDeviceTests` cover it.

`Game/Privacy/PrivacySettings` is the model of the Settings, Privacy toggles for the `analytics` and `diagnostics` purposes (#157, `docs/privacy.md` 6.2). The server keeps the choices; nothing is stored on the device. It is built with the `PrivacyPolicyVersion` the player saw and the app version, and refuses to be built without either, because every change is recorded as consent with both (`docs/privacy.md` 6.3). `Load` reads `GET /consents`; `SetAnalytics` and `SetDiagnostics` send `PUT /consents` `{analytics, diagnostics, policyVersion, appVersion}` through `ApiClient`, so they are signed with the request MAC, only after a load and never while another request is in flight. `Analytics` and `Diagnostics` change only to what the server answered, and `Changed` is raised only when a value really changes. The model also drives the client gates through `Game/Privacy/ConsentGates`, the same gates the startup uses: turning a purpose off withdraws it at once, before the server answers (`AnalyticsQueue.Withdraw` drops the queued events, `ErrorReports.Withdraw` stops crash reports), and a purpose opens only when the server answers it is on. An answer with `analytics` on while the queue is withdrawn consents it with a new analytics id from the id source it was built with (`PrivacySettings.RandomAnalyticsId`, a random UUID in its 36-character form), so granting again after a withdrawal never reuses the old id (`docs/privacy.md` 6.2, rotation). The id is held in memory only. `PrivacySettingsResult.From` turns a reply into one `PrivacySettingsOutcome`: no response is `privacy.settings.offline`, the limiter's `rate_limited` is `privacy.settings.rate_limited`, a success and a lost session have no message key, and every other reply, including `consent.malformed`, `consent.context_required` and an unreadable success, is `notice.generic`; a failure keeps the last values the server sent and opens nothing, and a failed withdrawal stays withdrawn. The keys ship in the built-in bundle with `en` and `az` texts. The Settings screen rows are not built yet. `PrivacySettingsTests` cover it.

`Game/Privacy/DataExport` is the model of the Settings, Account data export button (#157, `docs/privacy.md` 8.3). `Request` sends `POST /account/export` with no body through `ApiClient`, so it is signed with the request MAC, and sends nothing while a request is in flight. `DataExportResult.From` turns the reply into one `DataExportOutcome`: a created export is `Ready` with the signed `Url` and `ExpiresAtUnixMs` for the screen to open with `Application.OpenURL`, and only an absolute `http` or `https` link with a readable `expires_at` counts, so any other link is never handed on; `export_cooldown` is `account.export.cooldown` with `RetryAtUnixMs` (0 when the server sent no readable `retry_at`); a server failure, including `export_unavailable`, is `account.export.unavailable`; no response is `account.export.offline`; the limiter's `rate_limited` is `account.export.rate_limited`; a lost session has no message key; and every other reply, including a 404 from a server without an export store and an unreadable success, is `notice.generic`. The link is held in memory only and never written to device storage. The keys ship in the built-in bundle with `en` and `az` texts. The Settings, Account screen is not built yet. `DataExportTests` cover it.

`Game/Privacy/AccountDeletion` is the model of the Settings, Account delete account button and of the cancel button on the pending state (#157, `docs/privacy.md` 8.2). Both need a fresh sign-in, so `Request` and `Cancel` take the provider the player signs in with and, through `IAuthTransport` and `IIdentityProvider` like `AuthSession.SignIn`, get a nonce from `POST /auth/nonce`, ask the provider for a new ID token (Apple gets the hashed nonce), then post `{provider, id_token, nonce}` to `POST /auth/deletion` or `POST /auth/deletion/cancel`. One request is in flight at a time, and a provider the device does not support sends nothing. `AccountDeletionResult` turns the answer into one `AccountDeletionOutcome`: an accepted request (202, also when the account was already pending) is `Pending` with `DeleteAtUnixMs`, the server's `delete_at` at the end of `AccountDeletionGraceDays`, shown by `account.deletion.pending` with the `deleteAt` timestamp argument (`account.deletion.pending_undated` when the date is unreadable); a cancel (204) is `Restored`; `in_match` is `account.deletion.in_match`; `no_deletion_pending` is `account.deletion.not_pending`; `account_unknown` (the player picked another Google or Apple account) is `account.deletion.unknown_account`; `banned` is `account.deletion.banned`; `deleted` is `account.deletion.deleted`; `token_expired`, `nonce_rejected`, `token_rejected` and a failed or unsupported provider sign-in are `account.deletion.sign_in_failed`; a closed provider sheet is `SignInCancelled` with no message key; no response is `account.deletion.offline`; the limiter's `rate_limited` is `account.deletion.rate_limited`; a server failure, including `provider_unavailable`, is `account.deletion.unavailable`; and every other answer, including `malformed` and `unknown_provider`, is `notice.generic`. A sign-in during the grace answers `deletion_pending` with `delete_at`; `AccountDeletionResult.TryPending` turns that `AuthResult` into the same `Pending` result, so the pending state shows the same date and offers only `Cancel`. An accepted request has already revoked every session on the server, so the screen signs out locally (`AuthSession.SignOut`) after `Pending`. Nothing is written to device storage. The texts ship in the built-in bundle as drafts with `en` and `az` texts. The screen, its warning text (coins, items and pass progress are lost, store purchases are not refunded) and the pending state screen are not built yet (#848). `AccountDeletionTests` cover it.

Three views bind these models; the prefab, layout, row labels and the screen's composition root are not built yet (#848). `Game/SettingsScreenView` binds `SettingsModel`: the `LanguageRow`, one `VolumeSliderRow` per audio group, toggle rows for reduce motion, haptics, automatic frame rate and battery saver, a dropdown of the rates `FrameRatePolicy.IsOffered` allows (rebuilt when the policy changes, so a lower graphics level drops the rates it forbids; picking one leaves automatic, turning automatic off keeps the rate in use), and the cache clear button, whose outcome shows its `CacheClearKeys` text. `Game/Privacy/ConsentSettingsView` loads `PrivacySettings` and `PushSettings` when they are not loaded yet and binds the analytics, diagnostics, gameplay and promotional toggles; each toggle shows only what the server answered, so a refused or failed change goes back to the kept value with its message. `Game/Privacy/AccountSettingsView` binds `DataExport` (a ready export goes to the link opener it is given, never to device storage) and `AccountDeletion`: delete opens the warning panel with one confirm button per offered sign-in provider and a keep button; an accepted request shows the pending panel with `account.deletion.pending` and signs out locally through `AuthSession.SignOut`, then calls the sign-out callback it is given. `SettingsScreenViewTests`, `ConsentSettingsViewTests` and `AccountSettingsViewTests` cover them.

## First-launch consents

`Game/Privacy/FirstLaunchConsents` holds the `analytics` and `diagnostics` choices a player makes on the first-launch consent step, before sign-in, and writes them at sign-in (#73, `docs/privacy.md` 6.1 step 5 and 6.3). It is built with the `PrivacyPolicyVersion` the player saw and the app version, and refuses to be built without either. `Choose(purpose, granted)` appends one choice; the choices stay in memory only and are never written to device storage. `Write` posts `{choices, policyVersion, appVersion}` to `POST /consents/first-launch` through `ApiClient`, with the choices in the order they were made, and sends nothing while a write is in flight or no choice is held. A written answer drops the choices it sent and carries the server's `{analytics, diagnostics}`, which is the server's record when the account already had one for that policy version; any other answer keeps every choice for the next `Write`. The first-launch screens are not built yet (#848). `FirstLaunchConsentsTests` cover it.

`Game/Privacy/ConsentStartup` applies the account's consents at every sign-in, so the analytics queue and the crash reporter open only for a purpose the server records as on (`docs/privacy.md` 6.1 to 6.3). `Game/PrivacyBoot.Start`, called by `NetBoot` once the API client and the session exist, builds it with `ConsentGates` over `AnalyticsBoot.Queue` and `CrashReportingBoot.Reports` and calls `SignedIn` with the account id on every accepted server hello. When the first-launch screens have handed it their choices (`Hold(FirstLaunchConsents)`), `SignedIn` writes them through `FirstLaunchConsents.Write` (step 5); otherwise it reads `GET /consents`. Either answer is the server's record, and `ConsentGates.Apply` opens or closes each gate to it: `analytics` on consents the queue with a new random analytics id if it is withdrawn, off withdraws it and drops what was queued; `diagnostics` on calls `ErrorReports.Consent`, off `Withdraw`. Nothing opens before the server answers, so a new install sends nothing until its choices are written. A failed write keeps the choices and a failed read opens nothing; both are tried again at the next accepted hello. A reconnect of the account already applied sends nothing; another account reads its own record. One request is in flight at a time. Withdrawal goes through `PrivacySettings` (Settings, Privacy), which closes the gate before the server answers. `ConsentStartupTests` cover it.

## Editor methods in CI

Without a local Unity license, an editor method that creates or changes assets runs in CI: `gh workflow run unity-editor.yml --ref <branch> -f method=HypeDomino.Editor.<Class>.<Method>`. The workflow runs the method in batch mode and uploads everything it changed under `client/` as `editor-changes.patch` (artifact `editor-changes`); `gh run download <run id> -n editor-changes` and `git apply editor-changes.patch` bring it into the branch. The method runs its work through `EditorMethod.Run`, as `ContentSetup.ApplyAndExit` does: it exits the editor and writes `Logs/editor-method-succeeded` on success. The builder step always reports a failed build, because no player is built, so the run fails only when that file is missing.

## Release build

`Editor/ReleaseBuild.BuildAndroid` builds the release AAB for one catalog version (`docs/content-delivery.md` 6): it sets the Addressables player version to `-catalogVersion <version>`, builds the scenes in Build Settings into `-customBuildPath` (default `Builds/hypedomino.aab`) together with the content, and fails when `ServerData/Android/catalog_<version>.bin` is missing. It restores the player version and the AAB switch afterwards. In CI: `gh workflow run release-build.yml -f catalog_version=<version>`. The workflow measures the download size with `bundletool` on the low, mid and high device specs in `tools/install-size/specs`, fails at 150 MB or more (`docs/performance.md` 3) and keeps the AAB, the size report and the remote folder as artifacts. `ReleaseBuildTests` cover the version rule and the remote folder.

The workflow also runs on every pull request that changes `client/`, `tools/install-size/` or the workflow:
- The catalog version is `pr-<number>`; the build is unsigned and nothing is uploaded.
- The size report is in the run summary.
- It is not in `CI complete`, so a build over the budget shows as a failed check on the pull request without blocking the merge.
- A newer push cancels the running build of the same pull request.

Optional arguments stamp the release, and the build restores the project settings afterwards:
- `-appVersion <major.minor.patch>` sets the version name, the form the server compares with the minimum version (`proto/README.md`).
- `-buildNumber <n>` sets the Android version code, 1 to 2,100,000,000.
- `-applicationId <package>` sets the Android package name.
- `-androidSigning <file>` signs with the upload key: a JSON file with `keystore`, `keystorePass`, `keyAlias` and `keyAliasPass`.
- `-crashReporting <file>` turns crash reports on: a JSON file with `dsn` and optional `environment` (Error reports above). Leaving it out builds without crash reports; a file without a `dsn` fails the build.

Every run passes the workflow run number as the build number, so build numbers only grow. Pushing a tag `client-v<major>.<minor>.<patch>` runs the same workflow as a release:
- The version comes from the tag, and the catalog version is `<version>-<build number>`.
- The package name is the repository variable `ANDROID_APPLICATION_ID`.
- The upload key comes from the `ANDROID_KEYSTORE_*` and `ANDROID_KEYALIAS_*` secrets (`docs/environments.md` 2.3). It is written to `client/Signing` for the build only and removed afterwards.
- The signed AAB goes to the Play internal testing track with `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`.
- When the secret `CLIENT_SENTRY_DSN` is set, its DSN and the variable `CLIENT_SENTRY_ENVIRONMENT` are written to `client/Signing/crash-reporting.json` and passed as `-crashReporting`; without it the run warns and the build sends no crash reports.

A tag run fails before the build when a variable or secret is missing. The iOS build and the TestFlight upload are not built yet.

## Safe area

`UI/Layout/SafeAreaFitter` sits on the root `RectTransform` of each screen and anchors it to `Screen.safeArea`, so camera holes, notches, the island and the home indicator never cover UI. It refits when the safe area or the resolution changes (rotation, split screen, a folding display) and does nothing on other frames. `SafeAreaAnchors` turns the safe area into anchors, clamped to the screen; an empty screen or safe area falls back to the full screen. The `SafeAreaTests` EditMode tests cover 20:9 Android with a camera hole, iPhone landscape and portrait, a 4:3 tablet and 16:9 without insets. The `AspectRatioTests` PlayMode tests render a `ScreenView` through a camera into a texture of each display size: every device of the matrix (`docs/performance.md` 1), 16:9, 21:9, a 4:3 tablet and a folding inner display, in portrait and landscape. On each one the short side must be 1080 units, the canvas must keep the display's aspect, and the safe content must keep its size and stay on screen. Orientation is still open (`docs/ui-motion.md` 9), so nothing here assumes one.

## Match loading

`Game/Match/LoadingCards.Read(view)` lays out the loading screen of `docs/ui-motion.md` 5 "Match loading": one `LoadingCard` per seat in the order of the screen (own team first), with its row, roster index, progress and status (loading, ready, or bot playing once the phase is over), and `Progress` for the overall bar. `LoadingReport.TryReport(loaded, ready, out intent)` returns the `LoadingIntent` to pass to `Session.Send` only when the progress reaches a new step of 10 or the scene becomes ready. It reuses one message, so neither allocates. `LoadingCardsTests` and `LoadingReportTests` cover them.

`Game/Match/MatchPrefetch.Start(view, manifest)` acquires, through the screen's `CosmeticStage.Stills`, the static sprite of the server's `table` and of each roster entry's avatar, frame and tile, once per address. Each id goes through `CosmeticManifest.ShownOf`, so the address is the `staticAddress` of the item the view will show: a `disabled`, unknown or empty id gives the type's default, and nothing is loaded when the type has none (`docs/cosmetics.md` 8.3). `Loaded` is the share of settled loads, a failed one included, and is what `LoadingReport.TryReport` takes; `Done` is part of `ready`. `Release` frees the art; call it after the match scene's views have acquired theirs, so the shared cache keeps it. ## Match layout

`UI/Match/MatchLayout` places the regions of the match screen inside the safe area (`docs/ui-motion.md`, Match layout): the seat panels, the hand along the bottom and the board in what is left. ## Hand

`Game/Match/HandChoice` decides what the local player may do with the hand from the latest `MatchSnapshot` (`docs/ui-motion.md`, Hand). It never works out a legal move: while playing it offers the tiles and ends in `legal_moves`; while opening it offers the forced tile to its seat, or any tile to both players of the opening team. A tap places a tile with one legal end at once and selects a tile with several; `TryChooseEnd` then places it. `EndPlacesOf` gives the centre of each legal end of a tile on the arranged `ChainLayout`, in board units around the centre of the board area, or that centre for an opening placement; `TryDrop` places a dragged tile at the nearest of those places within `size.touchTargetMin`. End turn (R-31), draw (R-22, R-23) and pass (R-21) are offered from `turn_placements`, the mode and the boneyard size. After any intent the hand takes no input until the next view, so a double tap never sends twice. Reading a view, tapping and placing the ends allocate nothing; the `HandChoiceTests` EditMode tests cover each rule.

## Turn timer

`Game/Match/TurnTimer` reads `turn_deadline_unix_ms`, `turn_seconds` and `turn_warning_seconds` from each `MatchSnapshot` and, on every `Tick` with the `ServerClock` of the connection, gives the time left, the ring fill (time left over the turn length) and `IsWarning` once the time left is at most the warning threshold (`docs/ui-motion.md`, Turn timer). ## Match screen

`Game/Match/MatchScreen` connects the connection to the match views. `Bind(connection)` follows `Session.ViewReceived` and `Session.HelloReceived` of the connection's session; `Unbind` stops both. Each `MatchSnapshot` goes, in order, to the table background, the seats, the `ScoreBoard`, `BoardChain.Arrange` on the table's board size and scale cap, then the arranged `ChainLayout`, the `TurnTimer` and the `HandChoice`, which offers only the tiles and ends of `legal_moves` (`docs/ui-motion.md`, Hand). A pass is the `SoundCues` pass rule (same board, same boneyard, no placement, the turn moved on); the label shows at the passing seat's `TableSide` through `PassNotice` and hides after its lifetime. The first view after a `ServerHello` shows no pass. `Tick(connection, now, reduceMotion)` runs every frame: it ticks the timer on the connection's server clock, moves the pass label and ticks the connection notices. Each view is also read into `Notices` (`MatchNotices`), and `IMatchHud.ShowNotices` is called only when the network notice, a seat badge, the AFK warning or the take-back banner changed. `TapTakeBack(connection)` is the take-back banner's tap (`TakeBackBanner.Tap`). The views come in through `IMatchTable` (background, seats, score, board) and `IMatchHud` (hand highlight, timer, pass label, connection notices), so the binder runs on snapshots without a scene. Input goes back as intents through `Connection.Send`, which records each turn intent in `RoundTrip` until its ack, so a move waiting more than 2 s for the server turns the network notice `Weak` and the ack clears it: `TapTile(index)`, `ChooseEnd(end)` and `DropTile(index, endPositions, drop)` send `PlaceTileIntent` with the tile and end `HandChoice` allows (`BOARD_END_UNSPECIFIED` for an opening), and `EndTurn`, `Draw` and `Pass` send `EndTurnIntent`, `DrawIntent` and `PassIntent` only when the view offers them (R-21, R-22, R-23, R-31). Nothing is sent before an accepted hello, and after one intent the hand takes no more input until the next `MatchView`, so a double tap never sends twice; the server still decides legality (`docs/ui-motion.md`, Hand). `MatchTable` is the `IMatchTable` over `TableBackground` (the equipped table from `MatchView.table` in a `TableView`; `TableBackgroundTests`), `SeatAvatars`, `ScorePanel.Show` with a `ScorePanelView`, `BoardTilesView` and the board region of `MatchLayoutView`; its `RefreshEffects` refreshes the table and the seats after an effect change. `Game/Match/MatchRoot` composes the match from one session: it builds the `MatchScreen` over an `IMatchTable` and an `IMatchHud`, and the `MatchLoading` over an `ILoadingScreen` with a `MatchPrefetch` on the stills cache the match views share (`CosmeticStage.Stills`), so the views' holds keep the prefetched art, and it takes the `MatchEmoji` of the match HUD as `Emoji`. `Bind(connection)` binds all three (the screen to the connection, the loading screen and the emoji to its session), for the life of the session rather than per `AppFlow` state, because the view that moves the flow into `Match` is already being raised when the flow changes and a handler added then would miss it. `Tick(connection, now, reduceMotion, sceneReady)` runs every frame: it reports the loading progress first, then ticks the screen, and on the first tick after the loading screen closes it releases the prefetched art once, because by then the same view has reached the table and the seats and they hold their own art (`docs/ui-motion.md`, Match loading). A match joined past the loading phase releases nothing. The emoji art is held by its own `EmojiArtShelf` until the match ends, so the loading release leaves it alone. `MatchRootTests` (EditMode) cover the shared bind, a relayed emoji reaching its side, the order of a tick, the release, unbinding (which also ends the match emoji and releases its art) and 0 B ticks. `MatchRoot.Show(view)` hands one view to the loading screen, the screen and the emoji in that same order. `Game/Match/MatchHost` owns the match's life in the app: it follows `AppFlow.Changed`, builds a `MatchRoot` when the flow enters `Match` and match views are attached, binds it to the connection and shows it the session's current view once (the view that moved the flow into `Match` is being raised when the root binds, so the binding alone would miss it; a finished or empty view is not shown), and when the flow leaves `Match` or the views detach it unbinds the root, releases any prefetched art still held and drops it, so the next match gets a fresh root. The views come in through the `IMatchViews` seam (`Attach`/`Detach`): the `IMatchTable`, the `ILoadingScreen`, the stills cache they share, the `MatchEmoji` and `Ready`, which is the `sceneReady` of the loading report. The HUD is `Game/Match/MatchHud`, a non-visual `IMatchHud` the host owns for the life of the app: it holds the `HandChoice`, the `TurnTimer`, the `MatchNotices` and the pass label of each `TableSide`, and counts a change for the hand, the notices and the pass labels (`HandVersion`, `NoticesVersion`, `PassVersion`), so a HUD view redraws only when a count moved; the timer is read every frame. `Clear` drops everything when a match starts or ends. `Game/MatchBoot` builds the host from `NetBoot` on `AppBoot.Flow`, `NetBoot.Connection` and `ContentBoot.Cosmetics` and ticks it every frame from its driver with `Time.realtimeSinceStartupAsDouble` and `MotionBoot.Motion.ReduceMotion`. `MatchHostTests` and `MatchHudTests` (EditMode) cover building on the view that enters the match without showing it twice, views attached mid-match, the ready report waiting for the views, teardown and art release on leaving, a fresh root per match, detaching, the HUD state and 0 B ticks with and without a match. `Game/Match/MatchSceneViews` is the `IMatchViews` of the match scene: a MonoBehaviour holding the scene's `MatchLayoutView`, `ScorePanelView`, `BoardTilesView`, the `AvatarView` of each `TableSide`, the `TableView`, the `LoadingScreenView`, the `MatchHudView`, the rarity table (`UI/Rarity/rarity-defaults.json`) and the built-in avatar and frame sprites. `Attach` builds one `CosmeticStage` (stills from Addressables; no loop source exists yet, so every cosmetic shows its static art), a `CosmeticEffectsLink` that refreshes the table, the seats and the loading screen on an effect change, the `MatchTable`, the `LoadingScreen` and the `MatchEmoji`, then attaches itself to the host; `Start` does this with `MatchBoot.Host` when the scene loads, and `Detach` (also on destroy) detaches it. `Ready` is true while attached. `MatchTable` reads the active manifest on every view and sets the layout's seat count from the view's mode, so 1v1 lays out two seats and 2v2 four. The board scale cap is `MatchSceneViews.NoTileSizeCap` (no cap) until the largest tile size is decided. `Game/Match/MatchHudView` draws `MatchHud` in `LateUpdate`, redrawing the hand, the notices and the pass labels only when their count moved and the timer every frame: each hand slot shows its tile's face from the `TileFaceSet` and its legal mark only when `HandChoice.IsSelectable`, the draw, pass and end turn buttons show only when the hand offers them, the timer ring is filled to `TurnTimer.Fill` in `color.gold.default` and turns to the `warning` fill role at the warning threshold, the network notice, the AFK warning, the take-back banner and each side's seat badge show their game string, and each side's pass label takes the `PassNotice` alpha and scale. Taps go to `MatchScreen.TapTile`, `Draw`, `Pass`, `EndTurn` and `TapTakeBack` of the live root and do nothing outside a match. The match scene and prefab, the emoji layer and wheel slots, end choice for a tile with several legal ends, dragging, the selection ring, the pass label text, the hand tile size and the seat box placement are open (`docs/ui-motion.md` section 9, `docs/tiles.md` section 6, `docs/art-direction.md` section 10). `MatchSceneViewsTests` and `MatchHudViewTests` (PlayMode) cover building the match on attach, the art requests of the table and seats, the seat count, the HUD reading the hosted hand, detaching, the hand faces and legal marks, the turn buttons, the ring fill and warning colour, the notices, the pass label and 0 B refreshes. Showing a view and ticking allocate nothing; the `MatchScreenTests` EditMode tests cover the order, the legal-move highlight, the timer, the pass label, the connection notices reaching the HUD only on a change, the `Weak` notice of a move waiting for its ack, the take-back tap, reconnects, unbinding, every intent, the double-send guard and 0 B on the tap-to-send path.

## Profile

`UI/Profile/PlayerProfile` reads `GET /profile/me` (`TryFromOwn(json)`) and `GET /profile/{account}` (`TryFromPublic(json)`) into the profile screen model, from server values only (`docs/privacy.md` section 5). The fixed fields come through `ProfileReplies` and `JsonUtility`; the two maps keyed by mode come through `Net/JsonMap`. The own profile's `stats.modes` gives `ModeStats(i)`: the server's `games`, `wins` and `losses` of each mode, in the server's order. The public profile's `ranked.ranks` gives `Rank(i)`: the rank label of each placed mode (`Gold II`, `Master`), which `Game/Ranking/RankBadge.TryRead` reads into a badge. A missing or `null` map has no entries. A reply that is not a JSON object, a map or mode entry of another kind, an empty mode, an empty or non-string label, or a counter that is missing, negative, fractional or above `int.MaxValue` refuses the whole reply, as a missing account id or nickname does. Reading the model allocates nothing; `PlayerProfileTests` cover it with the server's reply shapes.

`UI/Profile/NicknameRename` builds the rename intent for `PUT /profile/nickname` (`TryRequest(nickname)`, the typed text as is, blank text not sent) and reads its reply with `NicknameRenameOutcome.Read(json)`: `Accepted` with the server's new own profile, `Refused` with the server's reason code (`nickname.taken`, `nickname.cooldown`, ... as in `docs/localization.md` 5.5, shown through its string key) and the `retry_at` time when sent, or `Unreadable`. The client does not pre-check the text or the cooldown; the server decides. The own profile carries the server's `rename_required` and `rename_available_at` as `RenameRequired` and `RenameAvailableUnixMs`, and while a rename is required its `rename_appeal` as `RenameAppeal` (Appeals); `TryRenameSecondsLeft(clock, now)` counts down to it on the synced `Net/ServerClock` without allocating, and an unreadable `rename_available_at` refuses the reply. `NicknameRenameTests` cover it.

`Game/Profile/ProfileLoader.Load` sends `GET /profile/me` through `ApiClient` (refresh on `access_expired`) and answers one `ProfileLoadResult`: `Loaded` with the own `PlayerProfile` that `TryFromOwn` reads from that body, or the failure. A second `Load` while one is in flight sends nothing. A reply with `setup_required` (an account that has no profile yet) is `SetupRequired` with no profile and no key, so the screen goes to nickname setup instead of showing an error. No response is `profile.load.offline`, `429` is `profile.load.rate_limited`, a lost session has no key and goes back to sign-in, and every other reply, including a body that `TryFromOwn` refuses, is `notice.generic`. `LoadPublic(accountId)` sends `GET /profile/{account}` with the escaped account id (an empty one sends nothing) and answers `Loaded` with the public `PlayerProfile` that `TryFromPublic` reads, or the same failures; `404 profile.unknown` is `Unknown` with `profile.load.unknown`. One loader has one load in flight, own or public. The built-in bundle holds the `en` and `az` text of every key. `ProfileLoaderTests` cover both requests, the single load in flight, the setup reply, every failure and the built-in texts.

`Game/Profile/NicknameSaver.Save(nickname, done)` sends the rename intent `PUT /profile/nickname` through `ApiClient`, so it is signed with the request MAC, with the request `NicknameRename.TryRequest` builds: the typed text as is, and blank text sends nothing. One rename is in flight at a time. It answers one `NicknameSaveResult`: `Saved` with the own `PlayerProfile` the server returned, so the new nickname and the next `rename_available_at` come only from the server, or the failure. Each format and moderation reason of `docs/localization.md` 5.5 has its own key `nickname.rename.<reason>` (`invalid_length`, `invalid_characters`, `invalid_separators`, `mixed_scripts`, `digits_only`, `taken`, `unchanged`, `not_allowed`). `429 nickname.cooldown` is `Cooldown` with `nickname.rename.cooldown` and the server's `retry_at` as `RetryAtUnixMs` (0 when missing), for a countdown on `Net/ServerClock`; any other `429` is `nickname.rename.rate_limited`, no response is `nickname.rename.offline`, a lost session has no key and goes back to sign-in, and every other reply, including `400 malformed`, a reason a newer server adds, `5xx` and a body `TryFromOwn` refuses, is `notice.generic`. These keys ship in the built-in bundle with `en` and `az` texts. The rename price (#101) is not part of the reply yet. `NicknameSaverTests` cover the intent, the server's new profile, the blank text, the single rename in flight, every reply and the built-in texts.

`Game/Profile/PlayerReport.Send(target, reason, matchId)` sends the report intent `POST /reports` `{"target","reason","match_id"}` (`docs/localization.md` 5.8): the target's account id, one of the fixed reasons `offensive_nickname`, `offensive_room_name`, `impersonation`, `other` (`PlayerReportReason`), and the match id or an empty one. An empty target sends nothing, and one report is in flight at a time. The server owns every limit: a reporter over the daily or rejected limit still gets 202 `received`, so the client cannot tell and never counts. The reply is one `PlayerReportResult`: `202` is `Received` with `report.send.received` (the generic acknowledgement, not the outcome), `404 report.unknown_player` is `report.send.unknown_player`, `400 report.self` is `report.send.self`, no response is `report.send.offline`, `429` is `report.send.rate_limited`, a lost session has no key, and every other reply (`report.reason`, `report.match`, `5xx`) is `notice.generic`. The built-in bundle holds the `en` and `az` text of every key. `PlayerReportTests` cover the request of each reason, the empty match, the single report in flight, every reply and the built-in texts.

## Hype Pass

`Game/Pass/PassStanding` reads the `GET /pass` reply (`PassReply`, `JsonUtility`) into what the pass screen header and its two tracks show, from server values only (`docs/pass-missions-medals.md` sections 2 and 6). `TryRead` refuses a reply without a season, a level outside 1 to `levels`, XP below the level's start, a next level start not above the XP, an unreadable `ends_at` or a negative `level_coin_price` or `level_crystal_price`. The level bar fills from `level_xp` to `next_level_xp`; the last level has no next level and shows full. `StateAt(track, level)` is earned up to the server's level, upcoming above it, and every premium level is locked until the server reports `premium`. Nothing is claimed: the server grants each level the moment it is reached (PM-3), so the client sends no claim intent. `TrySecondsLeft` counts down to `ends_at` on the connection's `ServerClock` and gives nothing before the clock is synced. `StateAt` and the countdown allocate nothing; `PassStandingTests` cover them. `PassTracks.TryRead(json, levels)` reads the reply's `tracks`, which are maps keyed by level number, with `Net/JsonMap`. `TryRewardAt(track, level)` gives the `PassReward` the server sent for that level: its bundle `id`, `coins`, `crystals` (0 when left out) and `cosmetics` (none when `null`). A missing or `null` track has no rewards; a level with no entry has none either. A level key outside 1 to `levels` or not written as a plain number, or a reward without an `id`, with a negative or fractional amount or with cosmetics that are not strings refuses the whole reply. `PassTracksTests` cover it with the server's reply shape. `PassLane.Of(standing, tracks, manifest)` lays the season out as the screen's rows, one per level: `CellAt(track, row)` gives a `PassCell` with the level, its `State` (`IsLocked` for the lock indicator) and the `Reward`, or none for a level the server left empty. Its cosmetics are the `CosmeticItem`s the manifest renders (`live` or `retired`), in the reward's order, with their `Art` for `CosmeticImage`, so an animated item can play its loop; an id the manifest does not know or does not render is left out. Reading a cell allocates nothing; `PassLaneTests` cover it.

`Game/Pass/PassLoader.Load` sends `GET /pass` through `ApiClient` (refresh on `access_expired`) and answers one `PassLoadResult`: `Loaded` with the `PassStanding` and `PassTracks` of that one body, or the failure. A second `Load` while one is in flight sends nothing. The server's `404 pass.no_season` is `NoSeason` with the key `pass.no_season`; no response is `pass.load.offline`, `429` is `pass.load.rate_limited`, a lost session has no key and goes back to sign-in, and every other reply, including a body that `PassStanding.TryRead` or `PassTracks.TryRead` refuses, is `notice.generic`. These three keys ship in the built-in bundle with `en` and `az` texts. `PassLoaderTests` cover the request, the single load in flight and every failure.

`Game/Pass/PassLevelBuyer.Buy(standing, count, currency, done)` sends the level purchase intent of `docs/pass-missions-medals.md` 2.6, `POST /pass/levels` with `{"count","currency","request_id"}` (`currency` is `coin` or `crystal`), through `ApiClient`, so it is signed with the request MAC. The server takes the price from its config, checks the season, the count and the balance, and spends; the client sends no price. Nothing is sent for a count below 1 or above `MostLevelsFor(standing)`, the levels the shown `PassStanding` has left, and a second purchase while one is in flight sends nothing either. The request id is 32 random hex characters kept in memory only, reused for the same count and currency after an answer that does not settle the intent (no response, rate limit, a server error or an unreadable success), so a retry the server may already have spent repeats its earlier answer (`repeated`) and never spends twice; a purchase or a refusal settles it (`IsUnsettled`). It answers one `PassLevelBuyResult`: `Bought` with the `PassLevelsReply` as sent (season, count, currency, price, the level and XP reached, `repeated`) and the spent currency's `Balance` after the purchase, or the failure. The screen then loads `GET /pass` again, since the levels crossed and their grants come only from the server. `402 wallet.insufficient` is `pass.levels.insufficient`, `409 pass.level_count` is `pass.levels.too_many` and `409 pass.no_season` is `pass.levels.season_over`; no response is `pass.levels.offline`, `429` is `pass.levels.rate_limited`, a lost session has no key and goes back to sign-in, and every other reply, including `400 request.invalid` and a body without a season, count, level, known currency or with a negative price or XP, is `notice.generic`. These five keys ship in the built-in bundle with `en` and `az` texts. The price shown before the tap comes from `GET /pass`: `PassStanding.LevelCoinPrice` and `LevelCrystalPrice` are the reply's `level_coin_price` and `level_crystal_price`, and `PassLevelBuyer.TryPriceOf(standing, count, currency, out price)` gives the count times the level price of that currency, or nothing for a count outside 1 to `MostLevelsFor(standing)` or a reply without a price (an older server sends none, read as 0), so the button then shows no price rather than a guessed one. The shown price is display only: the purchase intent still carries no price, and the server charges from its config at the moment of the purchase. `PassLevelBuyerTests` cover the intent body, the counts that send nothing, the shown price, every reply, the single purchase in flight, when a request id is reused and the built-in texts.

## Emoji

`UI/Emoji` holds the in-match emoji of `docs/ui-motion.md` (Emoji wheel, #151). `MatchEmoji` follows the session through `MatchRoot`, but the wheel button, the message bubbles and the seat menu are not drawn yet, because the match HUD views do not exist.
- **`EmojiWheel`:** holds the equipped emoji, up to the slot count given to `Equip` and its own capacity, and opens and closes the wheel. `TrySend` returns the id to send as `EmojiIntent` and closes the wheel. After a send the wheel stays calm for `TokenEffect.EmojiDurationMs`, and `OwnEmojiShown` restarts that time when the player's own `EmojiShown` arrives.
- **`EmojiPop`:** the pop's scale and opacity at a given time, including reduce motion.
- **`UI/Motion/LoopArt`:** the static sprite and the loop frames with their frame rate. It picks the static sprite on `EffectLevel.Low` or when it has no loop.
- **`SeatEmojiLayer`:** prewarms `TokenEffect.EmojiPooled` `EmojiPopup` instances in `Build`, so build it when the match scene loads. It shows one emoji per seat anchor (a new one restarts the seat's popup) and returns a popup to the pool when its pop ends. `Tick`, the effect's update, runs inside the `Effect.emoji` profiler marker (`SeatEmojiLayer.ProfilerMarkerName`), so a `ProfilerRecorder` on that name reads the effect's CPU time per frame (`docs/ui-motion.md` 7, Measurement).
- **`EmojiArtShelf`:** turns an emoji `item_id` into the `LoopArt` that `SeatEmojiLayer` shows, from the manifest and the `CosmeticStage` caches. `Prefetch` loads the own equipped emoji at match begin. `Show(side, itemId)` hands the art to the show callback at once when its static art is loaded, or when it arrives; a newer emoji for the side replaces one still loading. An id the manifest does not render as an `emoji` is dropped. The loop is loaded on medium and high and used once loaded. `Clear` releases all held art at match end.
- **`SeatMessages`:** the quick message bubble of each table side: the shown text and its end, `TokenEffect.EmojiDurationMs` after it arrived. A new message replaces the side's message from the start.
- **`Game/Match/MatchEmoji`:** joins the wheel and the session for one match. `Begin` takes the local seat and mode, `TrySend` and `TrySendMessage` send `EmojiIntent` and `QuickMessageIntent` only on an accepted session, `TryPlace` routes `EmojiShown` to its table side and `TryShowMessage` puts the text of a `QuickMessageShown` key, in the viewer's language from `GameStrings`, on its side in `SeatMessages`. The mutes are cleared by `End` and by the next `Begin` and never stored. `Wear` keeps the own emoji loadout: the loadout's `emojis` and `emoji_slots` of a `GET /inventory` reply, or the `emojis` of a `PUT /inventory/equip` reply (a reply without a loadout changes nothing). `Begin` puts them on the wheel, up to `emoji_slots`, before the prefetch, so the wheel keeps the loadout the match began with, as the server does (`docs/anti-cheat.md` NT-9). `Bind(session)` feeds it the session: the first `MatchView` of a 1v1 or 2v2 match that is not finished calls `Begin` with the view's seat and mode and prefetches the wheel's emoji on the `EmojiArtShelf`, a finished view or `Unbind` calls `End`, which also clears the shelf, and each `EmojiShown` (`Place`) and `QuickMessageShown` is routed at the time of the clock it was built with, an emoji's art going to the shelf (`docs/ui-motion.md` 7, Seat mute, Match bounds).

## Error reports

`Core/Diagnostics/ErrorReports` is the consent gate of #182 (`docs/privacy.md` 6.2, OQ-5). Its `OnLog` matches `Application.LogCallback`: while the `diagnostics` purpose is off nothing is sent, and after `Consent()` every exception, error and assert goes to an `IErrorSender` as an `ErrorReport` (type, message, stack trace), without account or analytics id. `Withdraw()` stops it at once. The `ErrorReportsTests` EditMode tests cover the gate.

`Core/Diagnostics/SentryErrorSender` is the `IErrorSender` behind it, without a vendor SDK: it posts each report as a Sentry envelope over HTTPS with `UnityWebRequest` (`UnityEnvelopeTransport`) to the project of the DSN. The DSN is a build input, never code (`docs/environments.md` 2.5): `Editor/ReleaseBuild` writes `-crashReporting <file>` to `Resources/CrashReporting.json` for that build only, and `CrashReportSettings` accepts only a Sentry EU data region DSN (host ending in `.ingest.de.sentry.io`, `docs/privacy.md` section 2) without echoing a refused one. Without the file, or with an empty `dsn`, `Game/CrashReportingBoot` hooks nothing and `CrashReportingBoot.Reports` sends nowhere. With it, the boot subscribes `ErrorReports.OnLog` to `Application.logMessageReceivedThreaded` and pumps the sender once a frame; nothing is sent until the account's `diagnostics` purpose is on (`Game/Privacy/ConsentStartup`, First-launch consents).

Each event carries the release (`Application.version`), the environment, the log type, the OS and the device model (D-25) and the exception with its frames, oldest first, our `HypeDomino.` frames marked in app. It carries no user, no device id, no server name and no session, and tells Sentry not to infer the IP (`infer_ip: never`, `docs/privacy.md` 6.4). `ErrorScrub` removes UUIDs (account and analytics ids), email addresses, bearer tokens, JWTs and URL query strings from the message and the stack trace. One envelope is in flight at a time; at most 30 reports wait (the Sentry SDK default queue size) and more are dropped; a failed post drops its report. A 429 or an `X-Sentry-Rate-Limits` header for errors pauses sending for its `Retry-After` (60 s when absent, the Sentry SDK default) and drops what arrives meanwhile. Nothing is written to the device. The `SentryDsnTests`, `SentryEnvelopeTests`, `ErrorScrubTests` and `SentryErrorSenderTests` EditMode tests cover the DSN rule, the event, the scrubbing, the queue and the rate limits.

Not built yet: release health (sessions) and native crashes, which need the Sentry Unity SDK (crash-free sessions count native crashes, `docs/closed-beta.md` BS-1), and the IL2CPP symbol and mapping upload, which needs the CI token (`docs/launch-runbook.md` OI-6).

## Analytics

`Core/Analytics` is the client side of `docs/analytics.md` (#181). `AnalyticsQueue` takes events only while the `analytics` consent purpose is on (`docs/privacy.md` 6.4): before `Consent(analyticsId)` and after `Withdraw()` nothing is queued, and `Withdraw` drops what was queued. `Track` accepts only the client event names of `AnalyticsEvents`, with one label and one value. `Flush` hands one batch of at most `AnalyticsBatchSize` events to an `IAnalyticsSender`, one send at a time; a failed send keeps the batch, and a full queue (`AnalyticsQueueLimit`) drops its oldest event. Both sizes and the flush interval are the `AnalyticsBatchSize`, `AnalyticsQueueLimit` and `AnalyticsFlushSeconds` keys of the `liveops` remote config domain (`docs/analytics.md` 6), delivered in `ServerHello.analytics_config`; the queue starts with `AnalyticsSettings.Draft` (50, 500, 60 s, the server defaults) until the first accepted hello, with the batch size capped at `AnalyticsSettings.MaxBatchSize` (400) so a batch always fits the server's 64 KiB body limit. `Game/Analytics/AnalyticsTuning` reads each accepted hello: it resizes the queue (`AnalyticsQueue.Resize`, dropping the oldest events above a lower limit) and retimes the flush timer (`AnalyticsFlushTimer.Retime`, a changed interval restarts at the next tick); a hello without the values, or with values outside `AnalyticsSettings.Valid`, changes nothing. `Game/Analytics/ApiAnalyticsSender` posts a batch as `{analyticsId, events: [{name, label, value, clientTimeMs}]}` to `POST /analytics/events` through `ApiClient`, so it is signed with the request MAC; a 200 and the refusals that never succeed (400, 403 `analytics.consent_required`, 409 `analytics.id_taken`) take the batch out of the queue, everything else (offline, lost session, 429, 5xx) keeps it for the next flush (`docs/analytics.md` 4 and 5). `Core/Analytics/AnalyticsFlushTimer` flushes every `AnalyticsFlushSeconds` of real time and when the app pauses, and allocates nothing per tick. `Game/AnalyticsBoot.Start`, called by `NetBoot` once the API client exists, builds the queue with the sender and the device UTC time, and drives the timer from a hidden object. `Game/Analytics/AppAnalytics` tracks `app_open` once per run on the first frame the queue holds consent (its `Tick` runs from the same hidden object and allocates nothing), `sign_in` with the provider when `AuthSession` raises `ProviderSignedIn`, and `queue_join` with `ranked_1v1`, `ranked_2v2`, `casual_1v1` or `casual_2v2` when `MatchQueue` raises `JoinSent`; `NetBoot` hands it the auth session, the match queue and the network session (for `AnalyticsTuning`) through `AnalyticsBoot.Follow`. `Game/Profile/NicknameSaver` is built with the queue and tracks `nickname_set` when the server accepts a save (`docs/analytics.md` 2). `Game/Shop/ShopPurchase` takes the queue as an optional constructor argument and tracks `purchase_start` with the store product id when it hands that product to the billing SDK, and `purchase_cancel` with the same id when the store answers cancelled; without a queue it tracks nothing. `NetBoot` passes `AnalyticsBoot.Queue`, so `NetBoot.Checkout` tracks both once a billing SDK replaces `NoStoreBilling`. `screen_view` is not tracked yet. The queue stays withdrawn until the account's `analytics` purpose is on: `Game/Privacy/ConsentStartup` applies it at sign-in (First-launch consents) and `PrivacySettings` changes it. The `AnalyticsQueueTests`, `AnalyticsSenderTests`, `AnalyticsFlushTimerTests`, `AnalyticsTuningTests`, `AppAnalyticsTests`, `NicknameSaverTests` and `ShopPurchaseTests` EditMode tests cover these rules.

## Pooling and allocations

Anything that spawns more than once is pooled; a match frame allocates 0 B (`docs/performance.md` 3).

- Plain objects and collections use the engine pools in `UnityEngine.Pool`: `ObjectPool<T>`, `ListPool<T>`, `HashSetPool<T>`, `DictionaryPool<TKey, TValue>`. Warm each pool at load time so the frame loop only gets and releases.
- Scene objects use `Core/Pooling/PrefabPool<T>`: it instantiates `prewarm` inactive copies under one parent at load time, activates on `Get`, deactivates on `Release` and destroys only what exceeds `maxSize`. Size it for the worst case of the scene so a frame never instantiates.
- Runtime assemblies do not use `System.Linq`; iterate arrays and `List<T>` with `for`. `RuntimeCodeRulesTests` fails on any `System.Linq` outside `Editor`, `Generated` and `Tests`.
- No string concatenation, interpolation or `ToString()` in `Update`, input or animation code; text changes only when its value changes.
- The `PoolingTests` PlayMode tests assert with `Allocates.Nothing` (`Tests/Support`, see `docs/test-strategy.md`) that warmed pools cycle without allocating. Every new per-frame path adds the same assertion.
